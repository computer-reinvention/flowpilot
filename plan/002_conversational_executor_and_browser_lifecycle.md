# 002 — Conversational executor and browser lifecycle

## Outcome

Run the existing conversational agent as a remotely controlled, private browser session without changing its script/replay value or relying on a local terminal. Restore website state safely across graceful closes; report interruptions without replaying uncertain effects.

Prerequisite: completed 000 only. Use supplied fake control-service and interaction ports; no dependency on other parallel implementations.

## Ownership

Own `backend/tasks/{executor,runtime,browser_adapter,memory}.py`, extraction changes in `backend/repl.py`, `backend/repl_sandbox.py`, `backend/sandbox.py`, and new `tests/test_task_executor_*.py`. Do not edit `handoff.py`, control persistence/routes, bootstrap/contracts, Compose, Dockerfiles or Harp. Coordinate sandbox configuration through 000's settings, not new ad hoc environment reads.

## Implementation slices

1. Extract/inject browser creation, memory ownership and interaction transport from `BrowserSession`. Local `./chat` retains terminal questions, the loopback handoff default and identity locking. Hosted execution has no stdin fallback and never starts a per-session public/loopback help server.
2. Implement an internal Docker-network CDP adapter. The current `ChatSandbox` loopback-published port is for host-local use, not backend-container access. Hosted browsers publish no CDP host ports. Use the existing sandbox image and restore-before-launch/profile-archive safety semantics.
3. Derive private storage keys from authenticated account ID plus server-issued profile ID, never untrusted path segments, API-key strings or a client user header. Lock profile/memory access, serialize browser writes and prevent simultaneous processes opening one profile. Distinct profiles under one account isolate cookies/local storage/scripts/history; explicit profile/session reuse restores them. Preserve per-site script lookup and follow-up history. Bound/redact persisted task context and script metadata; do not persist transient question responses.
4. Implement the task executor port with atomic claim/generation ownership supplied by 001's interface. Publish progress/interaction/terminal events through that port. Restore durable session context for a new task; do not mistake that for recovering a suspended agent after restart.
5. Preserve saved-script replay, partial-state inspection, repair and observable completion checks. A run reports success only on actual completion evidence. Script reuse is scoped to the correct personal identity/site. No replay is allowed merely because a client retried an admission or status request.
6. Bridge input/confirmation/browser-help requests to 000's interaction channel. Keep browser/model work paused while waiting. Explicit decline is not approval; browser resolution requires inspecting current state before more effects. Enforce bounded waits and current task/pause generation.
7. Implement browser handle access for 003 only during the authorized active pause. Agent and human must never write concurrently; resume waits for in-flight human inputs and releases held keys/buttons. The assistance implementation owns its HTTP transport, not this stream.
8. Stop model subprocesses, timed script execution and browser writers on cancellation/deadline. Fence callbacks from old tasks, save/close within a budget and accurately report failure to stop. Distinguish completed, cancelled, interrupted and profile-recovery-required outcomes.
9. Implement idle eviction, graceful archive save and startup cleanup/quarantine by task/session labels. Do not globally kill unrelated flow/REPL containers. Failed profile save retains the previous archive and a bounded recoverable artifact instead of silently declaring persistence successful.
10. Make sandbox memory/CPU/PID/shared-memory controls configurable through 000. Reproduce the 256-PID failure before selecting a default; 1024 is a benchmark input, not an automatically justified universal setting. Admission and measured settings must agree.
11. Use 000's observation policy injection for Pi execution, completion and repair; 007 implements that policy and owns `pi_browser.py`/observation-related `runner.py` edits. Develop against the contract double. Do not reimplement freshness hashing or readiness waits inside the runtime, and do not bypass the injected guard during code-mode/reflex dispatch.

### C — read-only aggregate quarantine design / exact outstanding limits

No quarantine deletion, retention, quota implementation, history-pruning duplication, settings addition or peer-file change was made in this repair pass.

**Confirmed current behavior:**

1. `Repository.release_browser(profile_saved=False)` releases `reserved` and marks the profile recovery-required. This blocks reopening that profile, but permits a new profile/task. Repeated failures across fresh profiles can therefore accumulate an unbounded aggregate number of stopped containers and previous archives. `max_active_browsers`/`max_account_browsers` currently bound active reservations, not retained recovery artifacts. A per-profile recovery gate is not an aggregate retention limit.
2. `TaskSandbox._close` preserves the previous known-good archive and stopped container; `mark_recovery` records task/session/execution generation/container without overwriting an existing marker. A 256 MiB archive and 272 MiB source-tar budget constrain serialization, **not the Docker writable layer**. RAM/CPU/PID/shm knobs do not enforce disk limits. A adds approximately 30 MiB of configured rotated Docker log payload per container, not an aggregate container/storage bound or exact whole-filesystem usage bound.
3. Task recovery scans matching `task-host` and profile-key labels and uses profile flock; it does not delete artifacts by age. Enumeration/work is not currently batch/cursor bounded. Task-host identity depends on stable state-directory and network names; changed identities leave unmatched artifacts requiring explicit inventory/reconciliation. Unknown/malformed/unmatched containers cannot safely be assumed disposable.
4. Existing peer-owned history pruning retains profiles but can delete released terminal task rows. A future recovery-artifact inventory must therefore survive task-history pruning; task rows or old timestamps alone cannot remain its ownership/deletion authority. `ops_retention.py` intentionally handles traces only and is not a profile/container reclamation mechanism.
5. Legacy `SandboxManager.cleanup_orphans` still selects broad `flowpilot=sandbox` labels and removes untracked **non-task** containers without deployment/generation proof. The `flowpilot-task` exclusion protects hosted task recovery resources, but does not make legacy orphan cleanup deployment-safe for unrelated flow/REPL instances. This pre-existing legacy limit was inspected, not silently changed in a design-only quarantine pass. No live/global orphan sweep was executed.

**Fail-closed option using existing count settings (proposed, not implemented):**

- Reuse `max_active_browsers` and `max_account_browsers` as a conservative ceiling on **active + reserved worst-case recovery slots**, not just live browsers. Reserve a potential artifact slot in the same durable admission transaction, before browser creation. Successful archive/disposal releases it; failed save transfers it to a quarantine reservation rather than freeing capacity. Unknown orphan ownership/count at startup closes admission until reconciliation. Never evict a sole copy to make room.
- This can bound newly created artifact **count** under the one-container-per-admission invariant without inventing a new numeric knob, but changes admission/release semantics and availability (a few quarantines can deliberately stop new work). It requires shared approval and implementation in 001: current `release_browser(False)` frees the slot, and current profile deletion rejects any reserved lease. A generation-checked quarantine-resolution/deletion path must release a retained recovery slot only after proven safe disposal or explicit owner-authorized deletion. A runtime-only directory count/check before spawn cannot make this atomic with admission and is not sufficient.
- It cannot establish a byte quota using the existing settings. Even one browser can fill its writable layer; per-profile archives and clean profiles also consume storage independently. Free-space samples or Docker `SizeRw` readings are observations, not a hard reservation or protection against growth between checks.

**Exact additions required for a hard aggregate byte-bound implementation (proposal for owners, no defaults selected):**

Numerical values, the filesystem/storage-driver quota backend and accounting for prior archives/staging/log overhead require operator/product approval. If the selected Docker storage driver cannot enforce its requested writable-layer ceiling, hosted readiness/admission must fail closed rather than ignore it. Quarantine headroom must be reserved before starting a browser; reaching a threshold only after a save fails is too late. Shared/legacy writers on the same filesystem also require an isolated quota-capable namespace or explicit accounting; no byte-bound claim is valid otherwise.

- **Mechanism (`cc8da1d`):** `backend/tasks/memory.py:QuarantineLedger`, one private JSON record per profile key under `state_dir/quarantine-ledger/`, mutated only under a cross-process `flock`. After the durable claim-revision preflight and **before any runtime/container exists**, the executor reserves a worst-case slot. In-flight reservations count exactly like quarantines, so a new artifact cannot exceed a quota. A proven save releases the slot. A failed or unproven save converts it into a quarantine charged at `max(reserve, measured archive + Docker SizeRw)`. A ledger write failure leaves the slot reserved, so it is still charged. Exhaustion settles the task `failed` with typed `capacity_exhausted` (`profile_saved=True`, profile untouched). An already-quarantined profile gets `profile_recovery_required`. Neither case constructs a runtime or deletes, evicts or reuses any container, archive or marker. `recover` converts dead reservations into quarantines when a marker is retained, drops them when nothing was retained, and adopts unledgered markers. Owners are attributed from the marker's new `account_id` or a recovered lease. Unknown/unreadable owners are charged to every account. Only explicit profile deletion frees a slot, after container, archive and marker removal succeeds. A failed removal keeps both the artifact and its charge. Records live outside task history, so pruning cannot drop them.
- **Real defect found by the gate (`841b410`):** a budget-exceeding save abandoned Docker's `get_archive` stream, and the daemon then held the container lock. Inspect, stop and remove of the retained artifact timed out after 60 s until garbage collection.
