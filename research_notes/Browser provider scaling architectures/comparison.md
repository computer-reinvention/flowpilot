# Browserbase, Browserless, and Cloudflare Browser Run: scaling without losing tabs

Research cutoff: October 17, 2026. Primary documentation, Browserbase engineering posts, and Browserless source were inspected; Context7 was used for all three services. Public web search returned no results, so discovery proceeded through primary documentation indexes and the Browserbase blog. This is a bounded review, not proof that undiscovered measurements do not exist.

## 1. Which architecture improves concurrency while preserving isolation?

### Takeaway
Browserbase documents one browser per Firecracker-backed VM; Cloudflare explicitly recommends multiplexing tasks into tabs/isolated contexts of an existing browser when process isolation is unnecessary. Browserless exposes an especially transferable control plane: bounded execution concurrency, a bounded waiting queue, resource admission checks, and horizontally distributed browser workers with reconnect affinity.

### Cited Findings
- **Browserbase isolation:** the security documentation says one browser per dedicated VM, isolated subnet/firewalls, and destruction/recreation of the VM after each session. This is not a shared-browser-context isolation architecture. Its July 21, 2026 engineering article explicitly identifies Firecracker as its compute layer. — [Security architecture](https://docs.browserbase.com/account/enterprise/security); [Engineering: build vs. buy](https://www.browserbase.com/blog/build-vs-buy-agent-infrastructure)
- **Warm pools:** Browserbase's engineering article describes prebooted, idling browsers; dynamically sizing the pool; the spare-to-active ratio; and statistical multiplexing of independent customers' bursts to reduce spare capacity per active session. It explains the mechanism but does not disclose actual production pool sizes or a measured idle ratio. Its illustrative one-spare-per-active scenario is not a fleet measurement. — [Engineering: warm pools](https://www.browserbase.com/blog/build-vs-buy-agent-infrastructure)
- **Cloudflare contexts:** Browser Run recommends reusing sessions and opening tabs; tabs do not count as additional browser instances for concurrency or new-instance-rate limits. Incognito contexts isolate cookies, local storage, and cache. Its FAQ explicitly says to use a fresh browser for full process-level isolation and warns that heavy tabs can crash the shared browser. “Tens” of lightweight tabs versus “only a few” heavy tabs is qualitative advice, not a benchmark. — [FAQ](https://developers.cloudflare.com/browser-run/faq/)
- **Cloudflare coordination:** the session-reuse recipe supports multiple clients attached to one browser, one context per request, context cleanup, then disconnecting the client without terminating the browser. It recommends Durable Objects for user-to-session routing and coordinating conflicting operations. A session listing can race with expiry or capacity exhaustion, so its example tries other sessions before launching. The page was updated October 12, 2026. — [Reuse sessions](https://developers.cloudflare.com/browser-run/features/reuse-sessions/)
- **Browserless admission:** `CONCURRENT` caps executing sessions, `QUEUED` caps pending requests, and requests beyond both get 429. Defaults shown are 10 executing and 10 queued, not hardware-density claims. Optional `HEALTH` admission checks use CPU/memory thresholds; `/pressure` exposes running, waiting, resource load, and availability. — [Docker configuration](https://docs.browserless.io/enterprise/docker/config); [Limiter source](https://github.com/browserless/browserless/blob/main/src/limiter.ts)
- **Code-level confirmation:** `Limiter` extends a queue, initializes its concurrency from configuration, defines capacity as `length < concurrency + queued`, checks `monitor.overloaded()` before admission, and pushes bounded jobs with timeout handlers. The public source is stronger evidence for this mechanism than a marketing concurrency claim. The docs describe health rejection as 503, whereas the inspected limiter constructs `TooManyRequests` and invokes a route callback; exact wire status should be verified on the deployed route/version. — [Limiter source](https://github.com/browserless/browserless/blob/main/src/limiter.ts); [Configuration](https://docs.browserless.io/enterprise/docker/config)
- **Browserless scale-out:** documented NGINX least-connections routing spreads initial sessions across containers. Existing browser sessions belong to their original instance; reconnect and LiveURL must route to it. The docs warn that replacing the instance address with a shared load-balancer address can misroute reconnects. Adding instances scales the fleet; failover routing does not transfer an existing process. — [NGINX and session affinity](https://docs.browserless.io/enterprise/docker/nginx-load-balancing)
- **Do not copy obsolete preboot flags:** current Browserless documentation explicitly says `PREBOOT_CHROME` and several other v1 configuration variables were removed in v2. Historical preboot recipes are not evidence for current v2 behavior. — [Docker configuration migration notice](https://docs.browserless.io/enterprise/docker/config)
- **Browserbase admission is not a transparent queue:** concurrent-browser limits and session-creation-per-60-seconds limits are separate; exceeding either drops the creation request with 429. The docs recommend respecting `retry-after` and backoff. Organization/project allocations are service quotas, not physical-host densities. — [Concurrency management](https://docs.browserbase.com/optimizations/concurrency/overview)

### Inferences
- FlowPilot can retain its per-user Chromium/Xvfb isolation while adopting a global admission queue, per-host resource admission, user/session-to-host mapping, and scale-out. Async control code frees orchestration workers while waiting; it does not eliminate the RAM of the browser it controls. These are architectural deductions from the queue and reconnect designs above, not measured FlowPilot improvements.
- Warm capacity reduces launch latency and launch storms but consumes idle RAM. Pooling independent arrivals reduces spare-capacity overhead; it does not make each active tab intrinsically smaller.
- Context sharing can reduce repeated browser-process overhead, but changes the isolation and failure boundary. For mutually untrusted user sessions it is not equivalent to Browserbase's per-VM architecture or FlowPilot's per-user container boundary. Cloudflare's examples fit request/task isolation particularly well.
- A live-session router needs an ownership lease or equivalent coordination, stable tab identifiers, and serialization of conflicting commands. Keep initial placement separate from reconnect routing. Scale-down should drain occupied workers rather than assume load-balancer retry can restore tabs.

### Gaps
- No verified Browserbase production pool size, placement algorithm, host utilization distribution, or current per-host browser count was found.
- Browserless's open-source worker and enterprise/shared-fleet features are not identical. No claim here that every Browserless tenant is VM-isolated, or that its managed fleet universally shares one Chromium process.
- Cloudflare's public API guidance establishes context-sharing behavior, not a detailed physical-host placement or VM boundary for Browser Run.

## 2. What survives disconnection, process death, or a long idle period?

### Takeaway
There are three distinct capabilities: reconnecting to a live browser preserves tabs and in-memory state; restoring a persistent profile preserves selected disk-backed state; full memory/device snapshots could restore execution state but are not established as a browser-session product feature by these sources. Calling all three “persistence” obscures the critical tradeoff.

### Cited Findings
- **Browserbase live reconnect:** `keepAlive: true` leaves the session available on the same connect URL after disconnect. It continues until explicit `REQUEST_RELEASE` or session timeout and continues consuming browser minutes. Different scripts/tools may attach. — [Keep alive](https://docs.browserbase.com/platform/browser/long-sessions/keep-alive)
- **Browserbase Contexts are profiles, not Playwright incognito contexts:** the API restores Chromium user-data-directory content across new sessions. Documented contents include cookies, localStorage, IndexedDB, session storage, service workers, autofill, and preferences; HTTP asset cache is excluded. `persist: true` writes changes at session close, followed by a suggested synchronization delay of a few seconds. Docs advise avoiding simultaneous use of the same Context. — [Contexts](https://docs.browserbase.com/platform/browser/core-features/contexts)
- **Browserless makes the distinction explicit:** its Session REST API persists an isolated `userDataDir` across browser restarts. By default `processKeepAlive` is zero: reconnection starts a new process with a blank page, requiring navigation again despite restored cookies/localStorage. With a positive grace period, the same live process preserves open pages, scroll position, navigation history, and in-memory inputs. After expiry it falls back to profile restoration. — [Persisting state](https://docs.browserless.io/baas/session-management/persisting-state)
- **Browserless lifecycle caveat:** that documented `processKeepAlive` path requires Puppeteer's `browser.disconnect()`; `browser.close()` immediately terminates the process. The page explicitly says this feature is unsupported with Playwright because it does not expose the required disconnect method. Session `ttl`, connection `timeout`, and live-process grace time are separate clocks. `stop` deletes persistent session data. — [Persisting state](https://docs.browserless.io/baas/session-management/persisting-state)
- **Cloudflare live sharing:** its Puppeteer recipe closes the per-request context and disconnects the CDP client, leaving the shared browser alive until its idle limit. It explicitly warns that `browser.close()` terminates the browser and disconnects other clients. Context isolation does not coordinate browser-wide operations. — [Reuse sessions](https://developers.cloudflare.com/browser-run/features/reuse-sessions/)
- **Firecracker capability is not Browserbase product evidence:** Browserbase's May 11, 2026 Firecracker explainer describes freezing a VM and saving guest memory plus device state, then restoring it. That demonstrates a substrate capability; the article does not establish a Browserbase session hibernate/resume API or claim that `keepAlive` evicts guest memory. — [Firecracker engineering explainer](https://www.browserbase.com/blog/what-is-firecracker)

### Inferences
- For “do not lose my tabs while the agent awaits an LLM or a human,” decouple the automation connection from a live per-user browser's lifetime. Keepalive is the directly documented solution, with a real resource reservation.
- For long inactivity, profile restore alone cannot promise the original live DOM, JS heap, unsaved forms, network connections, or exact tab execution state. Even Browserbase's broad list of persisted profile data is not a promise of full-process restoration.
- A useful explicit product contract has tiers: **live reconnect** (exact process while leased), **profile resume** (login/storage restored; pages reconstructed), and potentially **snapshot resume** (requires a separately verified implementation). Snapshotting also needs answers about expired remote connections and external server-side state.
- To contextualize Kernel/Browser Use: require evidence for which tier each actually implements. Neither asynchronous Python nor a persistent-cookie feature by itself establishes hibernation or memory reclamation without tab loss.

### Gaps
- No public full-process browser hibernation implementation or guarantee was established for these three provider products in this review. This is an evidence limit, not a claim that internal snapshotting is absent.
- Durable Objects coordinating a remote browser should not be described as browser-memory hibernation without separate evidence.
- Client close/disconnect semantics are provider- and protocol-specific; do not mechanically copy a lifecycle recipe between Puppeteer, native Playwright, and CDP integrations.

## 3. What density measurements can be compared with 32 vCPU / 64 GiB?

### Takeaway
No directly comparable published benchmark of long-lived, per-user Chromium/Xvfb sessions on a 32-vCPU/64-GiB host was found. The useful published numbers are generic Firecracker VMM overhead and Browserless sizing recommendations; neither validates 60–70 active FlowPilot users per host.

### Cited Findings
- **Browserless sizing guidance:** its deployment table recommends 2 CPU cores/4 GB for 5–10 concurrent sessions, 4 cores/8 GB for 10–20, and 8+ cores/16+ GB for 20–50. These are workload categories and recommendations, not an experimental benchmark with URLs, tab counts, active duty cycle, latency SLO, Chromium version, and reproducibility data. Its guide also calls out Docker's 64-MB `/dev/shm` default and recommends increasing shared memory for production. — [Enterprise deployment, resource requirements](https://docs.browserless.io/enterprise/docker/enterprise-image)
- **VMM overhead, not browser RSS:** Browserbase's Firecracker explainer reports about 125-ms guest boot, less than 5 MiB VMM overhead per VM, and 150 VM creations/second on a host. It explicitly defines the memory figure as host bookkeeping **before guest workload allocations**. These are generic Firecracker claims, not measured Browserbase browsers per host, and the article provides no 32-vCPU/64-GiB browser workload benchmark. — [Firecracker explainer](https://www.browserbase.com/blog/what-is-firecracker)
- **Observability consumes capacity:** Browserbase's engineering post notes that video encoding thousands of concurrent streams competes with browsers for CPU on the same hosts. This makes recording/live-stream workload an important comparison dimension. — [Build vs. buy, observability](https://www.browserbase.com/blog/build-vs-buy-agent-infrastructure)
- **Tab count is not free capacity:** Cloudflare explicitly warns that all tabs use the browser's available resources and heavy pages can crash it. Its guidance to reuse tabs concerns quota efficiency and startup overhead, not unlimited physical density. — [Browser Run FAQ](https://developers.cloudflare.com/browser-run/faq/)

### Inferences
- Mechanically multiplying Browserless's 4-core/8-GB guidance by eight gives 80–160 sessions at 32 cores/64 GB. **Do not present this as a capacity estimate:** the source uses GB, not GiB; cores are not necessarily equivalent to the target vCPUs; workload, isolation, graphics, tab count, and headroom differ; linearity is unmeasured. This arithmetic is included only to expose why seemingly comparable vendor figures are insufficient.
- The assignment supplies 33 constrained synthetic FlowPilot tests at approximately 0.7 GiB and 0.35 core per session. Treat those as user-supplied context, not independently audited research evidence. Pure division produces about 91 RAM-limited or CPU-limited sessions before any reserves; the earlier 60–70 estimate simply adds implicit headroom and is **still unverified**. Averages also cannot bound synchronized navigation/JS/recording bursts or long-lived memory growth.
- Benchmark the actual proposed layout using representative tab counts and pages, warm-idle versus actively navigating versus LLM-wait duty cycles, long-lived RSS/PSS and host memory accounting, CPU throttling, p95/p99 action latency, OOM/crash rate, and recording/Xvfb overhead. Establish an admission target below the observed knee, rather than equating provider quota or configured queue concurrency with capacity.
- Most immediately transferable improvements are lifecycle decoupling, admission/queue control, session-affine scale-out, and selective warm spares. Process sharing or snapshotting could change density more substantially, but each requires an explicit isolation and state-preservation decision plus measurement.

### Gaps
- No primary measured host-density result found for Browserbase or Cloudflare Browser Run with enough machine/workload detail to compare to the target host.
- No measured per-session memory reduction for replacing FlowPilot's container boundary with a Firecracker VM or a shared browser context was established. Less than 5 MiB of VMM overhead is not less than 5 MiB per browser.
- The Browserless source citations point to mutable `main`, inspected during this research, rather than a pinned commit. The deployment recommendations are living docs; retain this research date when citing them.
