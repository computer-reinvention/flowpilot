# Browser Use open source and Cloud scaling architecture

Research cutoff/retrieval: October 17, 2026. Engineering posts below have explicit publication dates; rolling docs and GitHub main were retrieved on this date and are not immutable historical snapshots. Context7 was consulted (`/websites/cloud_browser-use`), but returned older `docs.cloud.browser-use.com/concepts/*` material; current official V4 documentation takes precedence. No service calls or mutations were made.

## What is open source, and what does Cloud actually disclose about isolation and scheduling?

### Takeaway
The MIT Python agent library is distinct from the hosted proprietary service. Cloud now publicly describes **two separate compute planes**: browser microVMs on Firecracker/EC2 and hosted-agent microVMs on AWS Bedrock AgentCore—not one shared Chromium process inferred from Python BrowserSession code. [GitHub README](https://github.com/browser-use/browser-use); [browser architecture, June 15, 2026](https://browser-use.com/posts/firecracker-browser-infra); [agent architecture, July 12, 2026](https://browser-use.com/posts/agentcore-migration)

### Cited Findings
- **Product boundary:** README: “A cloud browser hosts the browser; the fully hosted API runs the agent as well.” Python library runs locally/self-hosted with a chosen model and local or remote browser; Cloud SDK is a client, not publication of Cloud orchestration infrastructure. README explicitly identifies the Python library as MIT licensed. [GitHub](https://github.com/browser-use/browser-use)
- **Browser isolation, June 15, 2026**, Aitor Mato and Laith Weinberger: “Every Browser Use Cloud session runs in its own, tiny VM.” Context is browser sessions, each with headless Chromium, filesystem, cookies/cache/proxy/downloads. Firecracker runs nested on regular EC2 rather than bare metal. This is an actual first-party infrastructure disclosure. [Engineering post](https://browser-use.com/posts/firecracker-browser-infra)
- **Browser scheduling:** custom control plane picks a host with room, starts hosts as demand rises, and drains hosts by ceasing new placements. It tracks starting browsers, draining hosts and hosts excluded from receiving sessions in real time, rather than waiting for CloudWatch's typical minute windows. Hosts boot from prebuilt images and serve browsers about 30 seconds after launch. Stateless edge routers resolve browser placement through the control plane and forward raw CDP WebSocket bytes; they do not schedule browsers. [June 15 post](https://browser-use.com/posts/firecracker-browser-infra)
- **CPU scheduling details actually disclosed:** leave virtual CPUs unpinned during Chromium startup, pin after CDP-ready, allocate both sibling hyperthreads of a physical core used, give pinned vCPU threads real-time priority. The vendor reports a 1,000-browser test changing from 17% early losses to zero after the priority change. No per-host browser count is given. [June 15 post](https://browser-use.com/posts/firecracker-browser-infra)
- **Browser rendering:** “We run our browsers fully headlessly.” They describe a patched Chromium fork and fingerprinting, avoiding a display-server/compositor stack. This is directly relevant to FlowPilot's current full Chromium/Xvfb cost, but does not establish identical rendering compatibility for every FlowPilot workload. [June 15 post](https://browser-use.com/posts/firecracker-browser-infra)
- **Hosted-agent isolation/scheduling, July 12, 2026**, Larsen Cundric: AgentCore provisions/schedules one microVM per agent session; `runtimeSessionId = session_id`. Durable session-scoped 1 GB `/mnt/workspace`; control plane on ECS Fargate/private subnets/ALB autoscaling on CPU. Agent runtime and control plane scale independently. Runtime execution role is scoped to ECR/logging; session tokens arrive per invocation; control plane mediates real upstream credentials. [July 12 post](https://browser-use.com/posts/agentcore-migration)
- **Historical chronology matters:** February 25 post described agent sandboxes on Unikraft microVMs on dedicated AWS bare metal, distributed across metros, with idle suspend/resume. June browser post says Unikraft browser standby/wake/scale-to-zero worked, but EC2 fleet expansion was manual, motivating their own Firecracker fleet controller. July agent post supersedes February's agent runtime with AgentCore. Do not summarize all three as the current same infrastructure. [February 25](https://browser-use.com/posts/two-ways-to-sandbox-agents); [June 15](https://browser-use.com/posts/firecracker-browser-infra); [July 12](https://browser-use.com/posts/agentcore-migration)
- **Source inconsistency worth preserving:** July post broadly says every outbound call passes through the control plane, but its specific networking/file sections explicitly allow public HTTPS for browser CDP and direct presigned transfers. The narrower supported reading is credential mediation, not that every network byte transits the control plane. [July 12](https://browser-use.com/posts/agentcore-migration)

### Inferences
- FlowPilot can retain its external agent and use only standalone Browser Infrastructure/CDP; hosted AgentCore architecture is informative but not required for that integration. [README](https://github.com/browser-use/browser-use); [browser quickstart](https://docs.browser-use.com/cloud/browser/quickstart.md)
- A browser VM, an agent VM, an API conversation, an authentication profile, and a tab are different units. The posts and API semantics support independently managing them rather than treating them as one permanent per-user container. [June post](https://browser-use.com/posts/firecracker-browser-infra); [July post](https://browser-use.com/posts/agentcore-migration); [limits guide](https://docs.browser-use.com/cloud/guides/concurrency.md)

### Gaps
- Not disclosed in inspected primary sources: host instance types, RAM/vCPU budget per browser, oversubscription ratios, actual browsers per host, packing algorithm, fleet safety headroom, scheduler implementation/source, region-specific topology, crash recovery guarantees or live migration. Do not infer numerical density from stress-test size or from OSS BrowserSession.
- Searches for public infrastructure talks did not yield a verified Browser Use talk/transcript adding reliable current details. Findings rely on full first-party engineering posts, not unverified talk claims. The Unikraft March customer story is historical supplier evidence, not authority for current architecture.

## How do asynchronous work, live tabs, profiles, human control and suspend/resume behave?

### Takeaway
Cloud supports asynchronous runs and temporary reuse of a live browser, but **profiles preserve login/browser storage, not the old tabs and page state after browser teardown**. Startup-template snapshots and agent-workspace recovery must not be described as an exposed full-state browser hibernation product. [sessions](https://docs.browser-use.com/cloud/agent/sessions.md); [profiles](https://docs.browser-use.com/cloud/guides/authentication.md); [June post](https://browser-use.com/posts/firecracker-browser-infra)

### Cited Findings
- **Async hosted work:** create a run, retain its run/session IDs, poll status/events and obtain results. SDK client wait timeout is local and does not cancel the server-side run. Only one active V4 run per conversation; direct concurrent follow-up returns 409. Per-session queue holds 20 pending messages; queue-full returns 429; it is explicitly **not** a project-wide batch queue or capacity reservation. Queue messages may initially have null `runId`; `interrupt=false` preserves current work, `interrupt=true` cancels it. [limits](https://docs.browser-use.com/cloud/guides/concurrency.md); [sessions](https://docs.browser-use.com/cloud/agent/sessions.md)
- **Explicit recommended batch architecture:** “Keep a large batch in your application's own job queue. Admit a bounded number of jobs and leave the rest pending there.” Track job/session/run/browser IDs independently; stagger status polls and share a project request budget. [limits](https://docs.browser-use.com/cloud/guides/concurrency.md)
- **Conversation versus browser:** “A V4 session is a conversation. A run is one turn in that conversation. A browser is the live Chrome instance used for website interaction.” A conversation can have multiple browsers; extra tabs within one browser are not additional browser sessions. [limits](https://docs.browser-use.com/cloud/guides/concurrency.md)
- **Agent-browser idle lifetime:** default about 120 seconds after last run activity, effectively 2–3 minutes because cleanup runs every minute. V4 `keepAlive` is integer seconds 120–14400, inherited by follow-ups; null resets to 120. It cannot exceed browser's four-hour hard lifetime; free-tier and ZDR runs always use 120. V2/V3 boolean `keepAlive` is different and must not be mixed into V4 examples. [sessions](https://docs.browser-use.com/cloud/agent/sessions.md); [limits](https://docs.browser-use.com/cloud/guides/concurrency.md)
- **Critical exact quote:** “A later follow-up gets a fresh browser with the same settings and profile, but not the old tabs or page state.” Reusing the still-open browser emits `browser.reattached` rather than `browser.ready`. [sessions](https://docs.browser-use.com/cloud/agent/sessions.md); [limits](https://docs.browser-use.com/cloud/guides/concurrency.md)
- **Standalone browser lifecycle (most relevant to external agent):** creation returns browser ID, `cdpUrl`, `liveUrl`, `timeoutAt`; timeout is minutes, default 60, range 1–240. Public status enum is `active` / `stopped`. Closing CDP, Playwright `browser.close()`, or SDK `client.close()` does not stop the managed browser; explicitly stop through Cloud API. Unlike agent browsers, standalone browsers retain a concurrency slot until stopped. [create schema](https://docs.browser-use.com/cloud/api-v4/browsers/create-browser-session.md); [quickstart](https://docs.browser-use.com/cloud/browser/quickstart.md); [limits](https://docs.browser-use.com/cloud/guides/concurrency.md)
- **Profiles:** “A profile persists cookies, local storage, and login state across browsers.” Official illustration says browser 1 saves state when it stops, browsers 2/3 load that saved state. Guide says “Use one profile per end user.” A new browser loads the profile; this is not resumption of old loaded pages. Local-to-cloud profile sync is narrower: README says cookies only, not local storage, IndexedDB or extensions. [profiles](https://docs.browser-use.com/cloud/guides/authentication.md); [README](https://github.com/browser-use/browser-use)
- **CDP context:** official connection examples use existing default browser context (`browser.contexts[0]`) so profile cookies and managed settings apply. They do not describe multiple independent end-user contexts in one shared provider browser as the deployment model. [quickstart](https://docs.browser-use.com/cloud/browser/quickstart.md)
- **Human takeover:** live-view URL is interactive; guide asks to wait for run completion at a checkpoint before human interaction, set `keepAlive` (example 900s), let user act, then submit a follow-up to the same session. Treat live URLs as credentials. If browser expires, follow-up loses the human's page state. This supports serialized handoff, not evidence of race-free simultaneous human/agent writes. [human-in-loop](https://docs.browser-use.com/cloud/agent/human-in-the-loop.md)
- **Agent stop/resume is different:** July AgentCore post specifies 15-minute agent idle stop, 8-hour maximum agent lifetime; SQLite `bcode.db` on durable mount survives idle stop and session recycle, with mount wiped on runtime version bump or 14 days idle. Control plane is cold-recovery source of truth. These are agent-runtime/file-state semantics, not browser tab retention or a replacement for the separate four-hour browser limit. [July post](https://browser-use.com/posts/agentcore-migration)
- **Current startup optimization, June 15:** production resumes a snapshot “already booted and paused just before Chromium launches”; uses 2 MB pages, custom userfaultfd handler to prefetch hot pages, disables unnecessary PS/2 probing, and gets ready notifications via vsock/log instead of HTTP polling. Vendor reports final VM cold start <400ms and public create latency 825ms p50/1.35s p99 over 10,000 successful sessions. Intermediate 9.8s→3.1s numbers describe earlier memory optimization, not final end-to-end latency. [June post](https://browser-use.com/posts/firecracker-browser-infra)
- **Future versus delivered:** same June post: “Today, we snapshot the VM just before Chromium starts”; snapshotting after Chromium is running is “what we are working on next.” This is a clean startup template, not a per-user snapshot containing their open tabs. Historical Unikraft standby/wake claims exist, but do not establish a current public arbitrary-browser hibernate/full-memory-restore API. [June post](https://browser-use.com/posts/firecracker-browser-infra); [February agent post](https://browser-use.com/posts/two-ways-to-sandbox-agents)

### Inferences
- For FlowPilot's “async without losing tabs,” decouple scheduling from browser ownership: queue tasks while keeping the same browser alive and reconnecting by its ID/CDP endpoint. That preserves a live working context within lifetime limits, but costs live browser time. Recreating a browser from a profile is insufficient when unsaved forms, tab sets or current page state matter. [quickstart](https://docs.browser-use.com/cloud/browser/quickstart.md); [sessions](https://docs.browser-use.com/cloud/agent/sessions.md)
- Separate concurrently active users should map to separate browsers and user-specific profiles. A profile ID represents reusable authentication state, not a simultaneously shared live desktop. Exact concurrent reuse/write semantics for one profile require vendor clarification. [profiles](https://docs.browser-use.com/cloud/guides/authentication.md); [browser isolation](https://browser-use.com/posts/firecracker-browser-infra)
- Browser Use's architecture is evidence for isolation plus elastic admission plus efficient startup; it is **not evidence that long-lived tabs survive scale-to-zero under the current public contract**. [June post](https://browser-use.com/posts/firecracker-browser-infra); [sessions](https://docs.browser-use.com/cloud/agent/sessions.md)

### Gaps
- No verified current customer API found for suspend/hibernate/resume of an arbitrary populated browser with DOM, JS heap, sockets, unsaved form state and all tabs intact. Current docs instead explicitly lose old tabs after stop. Do not claim unsupported internal mechanisms never exist; say not publicly established.
- No published warm-pool size, ongoing hot-browser pool policy, or confirmation that June's post-Chromium snapshot roadmap shipped by cutoff was found.
- Profile concurrent-writer locking, merge/last-writer-wins behavior, timing/atomicity of saves, failure-time recovery and complete coverage of IndexedDB/sessionStorage/cache are not specified in inspected current profile guide. Simultaneous human/agent control arbitration is also unspecified.

## What are billing/concurrency limits and the resulting fit for FlowPilot?

### Takeaway
Browser time is cheap but not free while preserving a live browser. Standalone browsers consume concurrency for their entire live lifetime, whereas idle hosted V4 agent browsers are billable but exempt from session-slot accounting. [pricing](https://browser-use.com/pricing); [limits](https://docs.browser-use.com/cloud/guides/concurrency.md)

### Cited Findings
- Current pricing: **$0.02/browser-hour**, residential proxy **$5/GB**, hosted agent **model cost +20%**, plus browser time/traffic; pay as you go. Pricing page advertises $1 one-time signup credit while GitHub README says $15: real source mismatch; do not rely on signup-credit amount in sizing. [pricing](https://browser-use.com/pricing); [README](https://github.com/browser-use/browser-use)
- Standalone create API says charged upfront, unused time proportionally refunded on stop, billed rounded up to minute with minimum one minute; maximum session duration four hours. [create API](https://docs.browser-use.com/cloud/api-v4/browsers/create-browser-session.md)
- Current project qualifying lifetime payment tiers: $0→10 concurrent sessions; $100→50; $1,000→250; $5,000→500; $25,000→1,000. Highest applicable legacy/existing grant preserved; account-specific restrictions/externally billed paths can differ. `GET /api/v2/billing/account` reports authoritative project allowance; keys in a project share balance and capacity. Profiles have separate quotas. [limits](https://docs.browser-use.com/cloud/guides/concurrency.md)
- Exact accounting: “A V4 session takes one concurrency slot only while it has a queued or running run.” Idle agent browser takes no slot but remains billed until stop. “A standalone browser holds a slot until it stops.” These are entitlement rules, not measurements of allocated CPU or VM density. [limits](https://docs.browser-use.com/cloud/guides/concurrency.md)
- HTTP rate limits are separate: general project default `min(100,max(25,2×stored concurrency))` RPS; selected status reads `max(25,2×stored concurrency)` RPS. Edge limits increased September 9, 2026 to general 1,000 RPS / selected status 2,500 RPS per public IP over 300-second windows. Project windows are five seconds; response `X-RateLimit-Limit=125` means 25 RPS. Respect actual Retry-After. [limits](https://docs.browser-use.com/cloud/guides/concurrency.md)

### Inferences
- At advertised browser rate, 1,000 live browser-hours cost $20 excluding traffic/agent cost; 1,000 browsers simultaneously retained for one hour similarly cost $20 but require suitable concurrent entitlement when standalone. This is arithmetic, not a claim of available account quota, density or SLA. [pricing](https://browser-use.com/pricing); [limits](https://docs.browser-use.com/cloud/guides/concurrency.md)
- Practical fit: useful managed browser layer for external-agent async jobs and bounded human handoffs; poor evidence for replacing an indefinitely retained user desktop with transparent lossless hibernation. A four-hour lifetime and explicit tab loss after stop are material limitations for that goal. [create API](https://docs.browser-use.com/cloud/api-v4/browsers/create-browser-session.md); [human-in-loop](https://docs.browser-use.com/cloud/agent/human-in-the-loop.md); [sessions](https://docs.browser-use.com/cloud/agent/sessions.md)

### Gaps
- No measured FlowPilot workload cost/performance, tenant capacity guarantee, private enterprise exceptions, or public browser-state recovery SLA was established. Vendor benchmark numbers are reported claims, not independent replication.
- AgentCore's “no idle bill” describes the underlying agent runtime economics; it must not be used to promise free idle Cloud browsers, which current API docs explicitly bill. [July post](https://browser-use.com/posts/agentcore-migration); [limits](https://docs.browser-use.com/cloud/guides/concurrency.md)
