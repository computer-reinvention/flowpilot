# Kernel browser infrastructure — public-source research, 2026-10-17

## How does Kernel isolate and schedule browsers efficiently?

### Takeaway
Kernel uses a dedicated VM per browser, backed by a bare-metal data plane and a separate control plane. Its documented efficiency mechanisms are full-memory snapshots, copy-on-write forks, lazy/shared snapshot paging, deliberate CPU oversubscription, and hot pools—not merely asynchronous agent code or multiple tenant contexts in one Chromium.

### Cited Findings
- **Architecture evolution, explicitly documented:** Rafael Garcia, *Lessons learned from scaling Chromium on bare metal*, **2026-05-26** (date verified in page JSON-LD), describes an initial “Docker containers (no K8s)” warm pool, then Unikraft-based VMs, then a QEMU data plane for GPU browsers. The article says initial browser startup costs **5–10 seconds**, after which RAM is snapshotted to disk; restoration from NVMe is approximately **30 ms**. Quote: “most of them are RAM snapshots sitting on disk, not consuming CPU or memory.” This is a vendor engineering account, not an independent benchmark. [Source](https://www.kernel.sh/blog/scale)
- **Firecracker is documented, not assumed:** Steven Miller, *how to make firecracker fast(er) to start chromium in <20ms*, **2026-06-05** (JSON-LD), explicitly describes Chromium inside Firecracker microVMs. Generic initialization runs once to a reusable snapshot; each fork receives identity data in guest memory before resuming. Overlay disks and guest-memory files use copy-on-write; UFFD pages memory on access and permits shared snapshot page-cache benefits across forks. [Source](https://www.kernel.sh/blog/firecracker-faster)
- **Internal hot pool:** same June article says an adaptive controller targets hot capacity, with burst overflow using snapshot forks rather than full boots. Reported hot handoff **10–30 ms**, connection to Chrome **<80 ms**, hot misses **~1%**. Its closing claim is **<20 ms for 99%** of starts and **<550 ms for the other 1%**. These are separate reported measures, not a universal cold-start SLA; the article itself makes clear that the fastest path is a hot-pool hit. [Source](https://www.kernel.sh/blog/firecracker-faster)
- **Single-host runtime / fleet boundary:** Steven Miller, *introducing hypeman: our open source sandbox infra*, **2026-08-04** (JSON-LD), describes a control-plane service on a standard PaaS and a data-plane fleet of bare-metal servers. Quote: “cross-host scheduling, failover, and regional placement are handled outside of hypeman.” Hypeman manages one host. It limits CPU, memory, storage, disk I/O, bandwidth and vGPU profiles, and exposes admission oversubscription ratios. [Source](https://www.kernel.sh/blog/hypeman)
- **Backend diversity:** the August article says Firecracker wins on efficiency/speed, QEMU supports their NVIDIA vGPU needs, and Cloud Hypervisor is being explored for capabilities such as hot-plugging vGPU. Hypeman runs regular OCI images via a custom initrd, read-only root filesystem and per-guest writable overlay. Same-image VMs share a read-only disk; memory-snapshot forks use hardlinks and share page cache. Do not describe every October browser as a pure single-address-space unikernel or every GPU browser as Firecracker. [Source](https://www.kernel.sh/blog/hypeman)
- **Published density, with workload caveats:** August article reports “about **128 running chromium vms, at 8× cpu oversubscription**” per Hypeman host, with an illustrative **128-CPU host → 1,024 allocated vCPUs → 128 eight-vCPU VMs**. CPU driven by guest work is the hottest resource. It expects lighter workloads could reach thousands, but that is explicitly a projection, with mid-thousands requiring further accounting/lifecycle work. It reports a median browser lifetime of **4 minutes**, >1 million browsers/month, and possible customer bursts of **2,500 browsers/minute**. The headline reports snapshot forks in **330 ms**. None establishes density on a 32-vCPU/64-GiB host. [Source](https://www.kernel.sh/blog/hypeman)
- **Open source corroboration:** Hypeman README explicitly documents “Standby & restore — snapshot a VM to disk,” and the lifecycle command comment says “snapshot to disk, stop hypervisor.” It lists Cloud Hypervisor, Firecracker, QEMU and Apple Virtualization.framework. This is runtime capability evidence, not proof that every supported backend/configuration is deployed by Kernel. README `main` is mutable; retrieved 2026-10-17, not pinned/audited implementation. [Repository](https://github.com/kernel/hypeman) · [Raw README inspected](https://raw.githubusercontent.com/kernel/hypeman/main/README.md)
- **Customer-configured pools are another layer:** official pool docs describe fixed-size, fixed-configuration pools, filling over a few minutes, immediate acquisition or wait, no automatic extra browsers when all are acquired, and explicit release. Acquisition avoids the create rate limit and startup/restarts for custom settings. Idle capacity is unbilled but counts against concurrency. Do not conflate these pools with the provider's internal adaptive hot pool. [Source, undated live docs retrieved 2026-10-17](https://www.kernel.sh/docs/browsers/pools)
- **Current public allocation/quotas:** docs give default headful memory **8 GB**, headless **1 GB**, with non-GPU upgrades to 16 GiB headful / 2 or 4 GiB headless. Org browser concurrency tiers: **5 / 10 / 150 / custom**. These are product allocations and quotas, not measured RSS or host density. Marketing browser page says dedicated VM and **2 vCPU/session**, which differs from the August eight-vCPU density example; do not silently mix those configurations. [Limits](https://www.kernel.sh/docs/browsers/concurrency-and-limits) · [Browser specs](https://www.kernel.sh/browsers)

### Inferences
- FlowPilot could benefit from decoupling logical browser-session identity from active compute residency: keep a per-user snapshot while another user's VM occupies running capacity. This requires actual checkpoint/restore and lifecycle scheduling; changing the external agent to async alone does not implement it. Basis: [snapshot design](https://www.kernel.sh/blog/scale), [host resource model](https://www.kernel.sh/blog/hypeman).
- Copy-on-write/shared snapshot cache primarily amortizes common initialized state. It does not mean independently mutated pages/JS heaps cost zero RAM while active. The cited source describes shared base state and child writes, not unlimited active-memory deduplication. [Basis](https://www.kernel.sh/blog/firecracker-faster)
- The supplied FlowPilot ~0.7 GiB/0.35-core synthetic result and 64-slot forecast are task context, not facts verified by this research. Kernel's different workload, VM sizing and oversubscription measurements cannot validate that forecast. [Comparison basis](https://www.kernel.sh/blog/hypeman)

### Gaps
- No inspected source specifies the exact fleet scheduler, bin-packing policy, host autoscaler, placement store, cross-host snapshot transport, or current failover durability guarantees. No basis to infer Kubernetes usage from cloud-industry convention.
- No published apples-to-apples active Chromium host-density benchmark for the proposed FlowPilot hardware/workload; memory sizes, page complexity, simultaneous activity and latency SLOs are not matched.
- Older docs still label all sessions Unikraft unikernels and include a “Sub-millisecond cold starts” heading whose body says <20 milliseconds. Prefer dated, more detailed engineering accounts; neither wording proves truly sub-millisecond startup. [Older architecture page](https://www.kernel.sh/docs/info/unikernels)

## What survives waits, disconnects and suspension—and what does it cost?

### Takeaway
Kernel explicitly describes preserving complete browser RAM across VM standby, which is substantially stronger than saving a profile. However, current lifecycle docs say connected clients prevent standby, suspended sessions still consume customer concurrency slots, GPU browsers cannot enter standby, and network peers cannot be assumed to survive suspension unchanged.

### Cited Findings
- **Current operational contract:** standby occurs after **five seconds** with none of: CDP client, WebDriver/BiDi client, Live View viewer, in-flight computer-controls request. State stays the same and usage costs become zero; afterward the deletion timeout starts. **GPU browsers do not support standby.** [Standby, undated live docs retrieved 2026-10-17](https://www.kernel.sh/docs/browsers/standby)
- **Session != connection:** termination docs explicitly state Playwright/Puppeteer `browser.close()` does **not** delete the Kernel browser. Default timeout is **60 seconds**, configurable up to **72 hours**, beginning in standby. Explicit Kernel deletion ends it. FAQ says CDP WebSockets may close after about **one hour**, but the browser persists and the client can reconnect to the same `cdp_ws_url` within its lifecycle. [Termination](https://www.kernel.sh/docs/browsers/termination) · [FAQ](https://www.kernel.sh/docs/browsers/faq)
- **Critical quota distinction:** “Standby stops usage charges, not the concurrency slot. Delete the browser to release it.” Reserved pool capacity also counts even when unacquired. Thus “zero billed browser usage while waiting” does not mean “unlimited waiting users on a 150-browser account.” [Limits](https://www.kernel.sh/docs/browsers/concurrency-and-limits)
- **Full-state checkpoint evidence:** May engineering article explicitly describes capturing “the entire in-RAM state of a running browser instance” to disk; older architecture docs list cookies/session data, loaded page content and **DOM**, window/zoom, local storage, and active downloads/processes in snapshots. It claims millisecond restoration. [May 26 architecture account](https://www.kernel.sh/blog/scale) · [Undated architecture docs](https://www.kernel.sh/docs/info/unikernels)
- **A material documentation conflict:** the May article says an ingress proxy holds CDP connections while the VM sleeps and resumes the same connection, specifically for LLM/human waits. Current standby docs instead classify any connected CDP client as active. These describe different observable policies. For integration design, follow current lifecycle docs and disconnect clients to allow standby; do not promise transparent sleep merely because no CDP commands are being sent. [Older claim](https://www.kernel.sh/blog/scale) · [Current contract](https://www.kernel.sh/docs/browsers/standby)
- **Sockets/network state are not magically durable:** Hiro Tamada, *how our in-house go proxy rewrite made wakeups 92% faster*, **2026-09-01** (JSON-LD), describes per-VM Envoy sleeping with the browser and waking with stale upstream connections/configuration. First-connection failures after idle were **20–26.7%** in their measurements. They moved to an always-on host-side Go proxy, decoupling network management from the suspended VM, with fresh request paths and metro-level proxy hosts. This directly disproves interpreting VM-state preservation as an end-to-end guarantee that arbitrary network sockets remain valid. [Source](https://www.kernel.sh/blog/proxy)
- **Network performance claim caveat:** that September article claims **92% faster wakeups**, but defines post-standby latency as time to a **successful first network request**, not raw VM restore. Test harness used browser pools, **2,000 repeated acquisitions**, hot swaps and idle intervals up to **two hours**. Do not mix that percentage with cold-start timings. Numeric tables are embedded images, not transcribed here. [Source](https://www.kernel.sh/blog/proxy)
- **Durability limitation historically acknowledged:** May article says Unikraft snapshots were pinned to a specific host; host/disk/power failure could lose state. QEMU work was motivated partly by migration as well as GPU support. June discusses migration as exploration, not a blanket shipped guarantee. [May source](https://www.kernel.sh/blog/scale) · [June source](https://www.kernel.sh/blog/firecracker-faster)
- **Resource effect:** May account says sleeping snapshots consume neither active CPU nor memory, and August account says standby increases density because only running guests drive CPU demand. Disk snapshots, lifecycle operations, page cache, proxies and control-plane resources still exist; the publications do not quantify their aggregate overhead. [May](https://www.kernel.sh/blog/scale) · [August](https://www.kernel.sh/blog/hypeman)

### Inferences
- Preserving the **entire RAM image** strongly implies retaining tab renderers and their JS heaps as part of same-session restoration, rather than reconstructing pages from URLs. This is an inference from full-RAM checkpointing, not an independently tested Kernel promise specifically naming JS heaps. DOM preservation is explicitly documented. [Basis](https://www.kernel.sh/blog/scale) · [DOM claim](https://www.kernel.sh/docs/info/unikernels)
- A suspended browser is not progressing page JS, downloads or arbitrary async work while its hypervisor is stopped; “active downloads preserved” should mean resumable process state, not ongoing transfer during standby. Remote deadlines, auth expiry, WebSocket servers and TCP peers may advance or expire externally. [Stopped-hypervisor evidence](https://github.com/kernel/hypeman) · [Observed stale connections](https://www.kernel.sh/blog/proxy)
- A FlowPilot wait strategy should distinguish **agent coroutine paused**, **browser still resident**, **browser checkpointed**, and **browser deleted/profile saved**. Only the checkpointed state can free active browser residency while aiming to preserve arbitrary in-memory tabs. Keeping Live View/CDP attached is operationally significant under Kernel's current contract. [Basis](https://www.kernel.sh/docs/browsers/standby)

### Gaps
- No inspected source guarantees arbitrary TCP/WebSocket/WebRTC sockets survive, promises exact timer behavior or pending fetch completion, or specifies preservation tests for JS heap identity and CDP object handles across long suspension.
- No independent test performed. Exact snapshot storage billing/retention, time to checkpoint, dirty-RAM write amplification, and recovery behavior across host failure remain unquantified here.
- The current standby page enumerates connected clients and computer requests but does not fully explain every server-side asynchronous process/Playwright execution hold. Do not assume launching a background process necessarily prevents standby, or that it completes while suspended.

## How do profiles and pool reuse differ from preserving a running user session?

### Takeaway
A profile is a durable Chromium user-data-directory snapshot, not a full RAM checkpoint. Pools can reuse an unchanged live browser, but that hands its tabs and identity to the next acquirer; they are not a safe automatic user-session swap mechanism.

### Cited Findings
- **Profile scope:** official docs say profiles capture the browser's **user-data directory**, including cookies/auth sessions, local storage/site data, open tabs/browsing state, and Chromium preferences. Each browser loads a snapshot; changes persist only with `save_changes`. Saving occurs when the Kernel browser is deleted/times out; closing CDP alone does not save. [Profiles, undated live docs retrieved 2026-10-17](https://www.kernel.sh/docs/browsers/profiles)
- **Profile concurrency:** browsers do not receive each other's updates; saving replaces the complete stored profile rather than merging. Only one browser can safely write a profile at once. Pool-level profiles are read-only. Docs recommend one profiled browser with a tab per task for concurrent tasks belonging to one end user, versus isolated read-only copies for separate workers. [Source](https://www.kernel.sh/docs/browsers/profiles)
- **Pool reuse is literal live-state reuse:** `reuse: true` (default) returns the same browser without reset: cookies, local storage, logged-in sessions and tabs persist for the **next caller**. `reuse: false` destroys/replaces it. For per-user use, docs recommend acquiring a profile-free browser, attaching that user's profile with `save_changes: true`, and releasing with `reuse: false`. This preserves the profile, not the former VM RAM. [Source](https://www.kernel.sh/docs/browsers/pools)
- **Timeout/pool behavior:** idle browsers awaiting acquisition can wait indefinitely; timeout starts after acquisition and then follows regular browser inactivity rules. If an acquired browser times out, it is destroyed and replaced rather than returned with its same live state. [Source](https://www.kernel.sh/docs/browsers/pools)

### Inferences
- “Open tabs preserved” in profile docs must not be upgraded to “identical DOM/JS heap/pending requests preserved.” User-data-directory restoration is a different mechanism from restoring the RAM image. For arbitrary agent waits requiring exact live state, retain the same session/VM checkpoint; use profiles for durable identity and reconstructible browsing state. [Profile mechanism](https://www.kernel.sh/docs/browsers/profiles) · [RAM mechanism](https://www.kernel.sh/blog/scale)
- For FlowPilot, the useful architecture is an **active compute admission limit plus separately owned suspended user sessions**, with a durable routing identity, snapshot store and reconnect/wake proxy. Kernel shows that this approach can preserve browser RAM, but its public quota still counts dormant sessions; business limits and physical capacity are separate design decisions. [Runtime design](https://www.kernel.sh/blog/hypeman) · [Quotas](https://www.kernel.sh/docs/browsers/concurrency-and-limits)

### Gaps
- No inspected source explains every field Chromium restores for profile “browsing state” or guarantees unsaved form values/in-memory app state. Treat full-heap preservation as exclusive to the separately documented RAM-checkpoint mechanism unless tested.
- Research used Context7 `/kernel/docs` for lifecycle/pool discovery, then fetched primary official documentation and dated engineering articles directly. Live docs and repository `main` had no publication dates in inspected text; recorded as retrieved **2026-10-17**, not immutable historical versions. No accounts, cloud sessions, installations or production mutations were used.
