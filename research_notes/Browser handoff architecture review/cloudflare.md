# Cloudflare Browser Run human handoff architecture — October 17, 2026

## What is the supported devtoolsFrontendUrl and human-handoff workflow?

### Takeaway
Cloudflare provides a genuine human-control interface to the SAME remote browser tab, plus explicit handoff signaling. Its documented automation connection remains attached while awaiting human completion; this is not a switch into an undetectable, disconnected personal browser. [Human in the Loop](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/)

### Cited Findings
- Browser Run is the new name for Browser Rendering and runs “headless Chrome on Cloudflare's global network.” Browser Sessions support Playwright, Puppeteer and CDP, whereas Quick Actions are stateless tasks. [Overview](https://developers.cloudflare.com/browser-run/)
- “A browser session is one remote Chrome instance”; a session can contain multiple tabs, and Live View connects to a page target. Opening the frontend URL opens Cloudflare's hosted interface, not the destination site in the human's local profile. [Live View, updated October 14, 2026](https://developers.cloudflare.com/browser-run/features/live-view/)
- Exact new-session REST route: `POST https://api.cloudflare.com/client/v4/accounts/$ACCOUNT_ID/browser-run/devtools/browser?keep_alive=600000&targets=true`, authenticated with a server-side bearer token with Browser Rendering Write permission. Response contains `sessionId`, per-target `devtoolsFrontendUrl` and `webSocketDebuggerUrl`, plus a browser-level `webSocketDebuggerUrl`. The frontend opens the UI; page WebSocket connects a CDP client to the tab; top-level WebSocket connects a CDP client to the browser. [Live View](https://developers.cloudflare.com/browser-run/features/live-view/)
- Existing session: `GET .../browser-run/devtools/session`, then `GET .../browser-run/devtools/browser/$SESSION_ID/json/list`, choose a target by URL/title, and open its `devtoolsFrontendUrl`. Custom links: `POST .../browser-run/devtools/browser/$SESSION_ID/live_view` with `mode`, `targetId`, and `expiresInMs`. [Live View](https://developers.cloudflare.com/browser-run/features/live-view/)
- CDP route: create a page CDP session, then send `Cloudflare.getLiveView({mode: "tab", expiresInMs: 300000})`; result contains `devtoolsFrontendUrl`. For Playwright the documented connection is `chromium.connectOverCDP(wss://api.cloudflare.com/client/v4/accounts/${ACCOUNT_ID}/browser-run/devtools/browser?keep_alive=600000, {headers:{Authorization: ...}})`, followed by `context.newCDPSession(page)`. [Human in the Loop](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/)
- Structured handoff: subscribe to `Cloudflare.handoffComplete` before sending `Cloudflare.handoff({instructions, timeout})`; share the Live View URL, wait for operator Done/Failed or timeout, inspect `success`/`reason`, and resume. Only `mode: "tab"` supports structured handoff. `targetId` defaults to the CDP session's page. Handoff timeout is optional, max 30 minutes; unspecified means no handoff timeout. `Cloudflare.getHandoffState` reports active state. [Docs](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/); [official documentation source, Beta metadata](https://raw.githubusercontent.com/cloudflare/cloudflare-docs/production/src/content/docs/browser-run/features/human-in-the-loop.mdx)
- The documented script awaits the event on the existing CDP connection; there is no disconnect/detach step. The simpler manual approach explicitly retains automation and polls DOM conditions or waits for navigation while the human acts. [Docs and complete examples](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/)
- `Cloudflare.*` commands are service extensions, “only available when connected to a Browser Run session”; they are not standard local Chromium CDP methods. [Human in the Loop](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/)
- Modes: `tab` displays one interactive page without DevTools panels, `full` displays browser UI and tabs, `devtools` exposes Elements/Console. For an inspector-form URL, replace `https://live.browser.run/ui/inspector?wss=` with `devtools://devtools/bundled/inspector.html?wss=` to open Chrome-native remote DevTools. This works only in Chrome and only for devtools mode. [Live View](https://developers.cloudflare.com/browser-run/features/live-view/)
- URLs contain a signed JWT, are bearer credentials, and default to a five-minute connection-start deadline (custom minimum one minute, maximum one hour). Expiry does not terminate an already-established connection; that lasts while the session lives. REST-only readonly guardrails block navigation, input and JavaScript evaluation for that viewer connection, not other automation connections. [Live View](https://developers.cloudflare.com/browser-run/features/live-view/)

### Inferences
- “Human takeover” means workflow/input-control handoff, not removal of CDP, browser replacement, transfer of cookies to the user's local Chrome, or guaranteed erasure of automation signals. The sample's retained CDP listener and manual DOM polling directly undermine the claim that disconnecting automation is required. [Supporting examples](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/)
- For local headless Chromium controlled by Playwright/Pi, replicate the same-session interaction and pause/resume contract using local infrastructure; Cloudflare's proprietary methods cannot simply be sent to ordinary Chromium. A headed window or secure remote interactive viewer is a UI design choice, not a proven anti-bot fix. [Service-only commands](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/); [headless service](https://developers.cloudflare.com/browser-run/)

### Gaps
- The reviewed public documentation does not specify whether structured handoff rejects all competing automation commands server-side. Do not claim an enforced exclusive controller lock; coordinate your own script and concurrent agents.
- No FlowPilot implementation was inspected in this research assignment. These findings provide comparison criteria, not proof of a particular local defect.

## What persists, who owns the session, and is it headed?

### Takeaway
The browser remains a Cloudflare-hosted headless session, shareable by concurrent clients in current releases. Session continuity is distinct from durable saved authentication state, and disconnect/close semantics depend on the client and connection method. [Overview](https://developers.cloudflare.com/browser-run/); [Reuse sessions](https://developers.cloudflare.com/browser-run/features/reuse-sessions/); [Playwright](https://developers.cloudflare.com/browser-run/playwright/)

### Cited Findings
- Current reuse docs explicitly allow multiple independent CDP clients to connect concurrently. Minimum Cloudflare library versions: Puppeteer 1.1.0 and Playwright 1.3.0. Older libraries use a legacy single-connection workflow. Thus an old exclusive `connectionId` ownership model must not be generalized to the current service. [Reuse sessions, updated October 12](https://developers.cloudflare.com/browser-run/features/reuse-sessions/)
- Puppeteer `browser.disconnect()` ends its connection without terminating the shared browser. `browser.close()` terminates it and disconnects every client. Browser contexts isolate cookies/storage but do not coordinate browser-wide operations. Durable Objects are recommended to route users to sessions or coordinate conflicting operations. [Reuse sessions](https://developers.cloudflare.com/browser-run/features/reuse-sessions/)
- Cloudflare Playwright docs distinguish `close()` for a browser obtained with `connect` (disconnect session) versus `launch` (close session). The acquire/connect example retains the session across client close calls. Do not transplant Puppeteer lifecycle semantics into Playwright uncritically. [Playwright session reuse](https://developers.cloudflare.com/browser-run/playwright/#session-reuse)
- Current limit is 60 seconds inactivity by default, configurable with `keep_alive` up to **20 minutes**. There is no fixed lifetime while active, but sessions also close during Browser Run releases. Dashboard-created sessions default to five minutes inactivity. [Limits, updated October 14](https://developers.cloudflare.com/browser-run/limits/); [Live View](https://developers.cloudflare.com/browser-run/features/live-view/)
- Explicit storage persistence is separately documented: `context.storageState({indexedDB:true})` exports cookies, localStorage and IndexedDB to KV, and a later context restores the saved state. This is not a full running-process snapshot. [Playwright storage state example](https://developers.cloudflare.com/browser-run/playwright/#storage-state)
- Hosted product is explicitly headless. Headful mode is separately labeled experimental local debugging through `X_BROWSER_HEADFUL=true npx wrangler dev` or `vite dev`. Live View's visual interface is not evidence that hosted production sessions become local headed Chrome. [Overview](https://developers.cloudflare.com/browser-run/); [Playwright local debugging](https://developers.cloudflare.com/browser-run/playwright/#local-debugging-with-headful-mode-experimental)

### Inferences
- Preserve the exact page/context/session throughout handoff; opening the site in a different local browser would not reproduce Cloudflare's architecture. Keep the session alive separately from the handoff timeout and link deadline. [Live View](https://developers.cloudflare.com/browser-run/features/live-view/); [Limits](https://developers.cloudflare.com/browser-run/limits/)
- For local FlowPilot/Pi, a single session owner/coordinator should gate agent mutations during human control, maintain target identity, accept explicit Done/Failed, and verify application state before resumption. This is a recommendation inferred from the official workflow, not a claim about current local code. [Handoff](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/); [coordination guidance](https://developers.cloudflare.com/browser-run/features/reuse-sessions/)

### Gaps
- Context7 returned older cached snippets with a 10-minute maximum and old `browser-rendering` endpoint names. Fresh official pages fetched in this run say 20 minutes and use `browser-run`; prefer the fresh October 14 pages for current limits. Legacy endpoint compatibility was not tested.
- No service runtime source was inspected, so details of internal rendering/streaming transport and server-side arbitration are unverified.

## Can a human solve third-party Cloudflare challenges, and does Runtime.enable explain FlowPilot?

### Takeaway
Human intervention is a supported workflow, including CAPTCHA as a generic use case. It is explicitly NOT a guarantee that Cloudflare challenges or third-party bot policies will accept the session. No reviewed official evidence establishes Runtime.enable as the specific cause of FlowPilot's failure. [Handoff bot-detection warning](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/); [Challenge browser support](https://developers.cloudflare.com/cloudflare-challenges/reference/supported-browsers/)

### Cited Findings
- The same page that advertises MFA/SSO/CAPTCHA also states: “Browser Run requests are always identified as bot traffic. Even with a human controlling the session, some third-party services may still block the request.” The source file contains that warning too, so it is not merely search-result interpretation. [Docs](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/); [official source](https://raw.githubusercontent.com/cloudflare/cloudflare-docs/production/src/content/docs/browser-run/features/human-in-the-loop.mdx)
- FAQ: “Browser Run requests are always identified as bot traffic by Cloudflare.” Enforcement is the website customer's choice. Allowlisting guidance applies to **your own website**, via Enterprise Bot Management fields and WAF rules; it does not give a caller authority over third-party site policy. [FAQ](https://developers.cloudflare.com/browser-run/faq/#will-browser-run-be-detected-by-bot-management)
- Cloudflare challenges documentation explicitly says “Automated browsers are not supported for solving production challenges” and names Selenium, Puppeteer, Playwright, and Cypress as unsupported frameworks for that purpose. Turnstile test keys are the documented testing path. [Supported browsers, updated August 18](https://developers.cloudflare.com/cloudflare-challenges/reference/supported-browsers/)
- Browser Run cannot configure per-request IP rotation; traffic originates on Cloudflare networks and includes identifying automatic headers. Changing user-agent does not bypass bot protection. [FAQ](https://developers.cloudflare.com/browser-run/faq/#does-browser-run-rotate-ip-addresses-for-outbound-requests); [Playwright](https://developers.cloudflare.com/browser-run/playwright/#set-a-custom-user-agent)
- Official challenge troubleshooting discussion notes developer-tool overrides and device emulation may change browser signals; it does not state that merely attaching CDP always causes rejection or that detaching guarantees acceptance. [Supported browsers](https://developers.cloudflare.com/cloudflare-challenges/reference/supported-browsers/)

### Inferences
- The AI Overview's broad implication that Browser Run human handoff solves third-party Cloudflare blocks omits an express product limitation. An interactive CAPTCHA and an anti-bot rejection of the browser/network are different obstacles; successful human input alone need not change the latter. [Explicit warning](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/)
- Headless alone is not proof of an incorrectly implemented handoff: Cloudflare itself offers handoff on a headless service. Conversely, copying its Live View UX does not make local Playwright supported for production challenge solving. [Overview](https://developers.cloudflare.com/browser-run/); [challenge limitations](https://developers.cloudflare.com/cloudflare-challenges/reference/supported-browsers/)
- Recommended next diagnostic boundary: first verify FlowPilot preserves the same live session/tab and truly pauses agent input; then determine whether the failure is viewer/control delivery versus a target-site challenge rejection. Treat Runtime.enable as a hypothesis requiring exact version/trace evidence, not an RCA or mandate to implement stealth patches. [Handoff reference](https://developers.cloudflare.com/browser-run/features/human-in-the-loop/)

### Gaps
- Targeted searches surfaced third-party Runtime.enable/CDP-detection articles, but no official Cloudflare confirmation of the specific current detector mechanism. Those articles were not used as evidence that Cloudflare uses that mechanism or that disconnecting fixes it.
- No challenge was executed, no account mutated, no local code altered, and no causal experiment run. There is no basis here to assert FlowPilot's exact bug, challenge pass rate, or that headed mode/detachment would fix it.
