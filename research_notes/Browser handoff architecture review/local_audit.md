# FlowPilot human browser handoff: read-only local architecture audit

## 1. Does pausing the agent actually give the human an uninstrumented browser?

### Takeaway
No. The implemented handoff pauses task execution while retaining browser automation connections. This is a functional human-input handoff, not a detach-all-clients/native-browser takeover. That distinction is confirmed; its contribution to the reported Cloudflare denial is not established.

### Cited Findings
- Local REPL launches a Playwright persistent Chromium context, then connects browser-use to that same browser over CDP. Both survive human assistance; teardown happens at session exit. `keep_alive=True` is not a detach instruction. Evidence: [backend/repl.py:87–123](../../backend/repl.py#L87), [193–201](../../backend/repl.py#L193).
- Local handoff awaits a future, resolved by resume/cancel HTTP endpoints; no browser disconnect, Runtime disable, or observer shutdown occurs in that path. Evidence: [backend/handoff.py:137–157](../../backend/handoff.py#L137), [182–201](../../backend/handoff.py#L182).
- Agent-tool dispatch is serialized under an asyncio lock held across the awaited tool callback. Thus human-help blocks subsequent Pi-dispatched browser tools, even though the local `RunControl([False])` itself is not paused. This is stronger than merely informing the model to wait, but does not stop CDP listeners/background browser activity. Evidence: [backend/pi_agent.py:37–57](../../backend/pi_agent.py#L37), [backend/pi_browser.py:78–80](../../backend/pi_browser.py#L78), [backend/repl.py:267](../../backend/repl.py#L267).
- Original/server runner uses `control.pause()` then awaits `control.checkpoint()`; RunControl only sets an event/boolean and optionally pauses the agent. Explorer custom `request_human_help` similarly sets `_paused`, calls `.pause()`, and polls for resume (300-second timeout). Neither primitive detaches browser clients. Evidence: [backend/runner.py:503–524](../../backend/runner.py#L503), [backend/replay.py:7–29](../../backend/replay.py#L7), [backend/explorer.py:483–511](../../backend/explorer.py#L483).
- Installed versions are browser-use **0.13.11** and Playwright **1.64.0**, based on local distribution metadata. These findings concern these installed files, not assumed upstream behavior. Evidence: [browser-use metadata:1–3](../../.venv/lib/python3.13/site-packages/browser_use-0.13.11.dist-info/METADATA#L1), [Playwright metadata:1–3](../../.venv/lib/python3.13/site-packages/playwright-1.64.0.dist-info/METADATA#L1).
- Playwright's Chromium page initialization explicitly sends `Runtime.enable`; renderer listeners include `Runtime.consoleAPICalled`, execution-context creation/destruction, and exceptions. It also creates isolated worlds and enables target auto-attach. These are framework-internal listeners: absence of application `page.on('console', ...)` does not mean Runtime is disabled. Evidence: [installed coreBundle.js:38937–39024](../../.venv/lib/python3.13/site-packages/playwright/driver/package/lib/coreBundle.js#L38937).
- browser-use actor `Page._ensure_session()` attaches a fresh session if absent and enables Page, DOM, Runtime and Network. `get_current_page()` constructs a new actor without a session ID; Pi observe/navigate obtain actor pages through `must_get_current_page()`. Separately, browser-use root connection initializes SessionManager and auto-attach; child attachment enables recursive auto-attach. Evidence: [actor/page.py:45–73](../../.venv/lib/python3.13/site-packages/browser_use/actor/page.py#L45), [session.py:1360–1377](../../.venv/lib/python3.13/site-packages/browser_use/browser/session.py#L1360), [session.py:1910–1927](../../.venv/lib/python3.13/site-packages/browser_use/browser/session.py#L1910), [session_manager.py:402–444](../../.venv/lib/python3.13/site-packages/browser_use/browser/session_manager.py#L402), [pi_browser.py:65–74](../../backend/pi_browser.py#L65).
- browser-use exposes a distinct `stop()` lifecycle that stops event buses/resets state; the handoff does not call it. Stopping browser-use alone would still leave Playwright's owner connection and viewer instrumentation. Evidence: [installed session.py:755–779](../../.venv/lib/python3.13/site-packages/browser_use/browser/session.py#L755), [repl.py:110–121](../../backend/repl.py#L110).
- `CDPSession.detach()` detaches that session only. Closing the persistent Playwright context closes the browser, so replacing pause with context.close is not a browser-preserving takeover. Evidence: [Playwright CDPSession documentation](https://github.com/microsoft/playwright/blob/main/docs/src/api/class-cdpsession.md), [persistent-context documentation](https://github.com/microsoft/playwright/blob/main/docs/src/api/class-browsertype.md).

### Inferences
- A genuine “no automation client during human control” contract is currently unmet. A “human controls the same still-instrumented page while task tools wait” contract is substantially implemented. Those are different acceptance criteria, not competing guarantees of site acceptance.
- Repeated actor-page creation is a concrete candidate for session accumulation: session creation is visible, but this audit did not measure live counts or prove a leak. A single temporary viewer session's detach cannot establish that all Runtime-enabled sessions are gone.
- Runtime-enabled sessions are confirmed instrumentation, **not proof of a currently effective Cloudflare detection technique**. No specific console-serialization or CDP-detection claim is established here.

### Gaps
- No connection inventory or protocol trace was collected from the active browser, deliberately. Actual live target/session counts and callback traffic during the reported pause remain unknown.
- The supplied Blinkit denial, `navigator.webdriver=true`, and `HeadlessChrome/156.0.8078.4` are coordinator-provided observations, not independently reproduced in this audit. No Ray ID/security event explaining the rejection was provided.

## 2. How do launch, profile, input and cleanup differ between original app and local REPL?

### Takeaway
The local REPL changed both browser ownership/launch and the control transport. It defaults to Playwright-launched headless Chromium with a persistent app-owned profile and a second browser-use connection. The original sandbox starts a headed Chromium process under Xvfb and adds an independent CDP viewer; neither path provides native OS input or automatically detaches automation on handoff.

### Cited Findings
- REPL defaults `headless=True`, uses a user-specific `browser` directory, does not select a Chrome channel/executable, and passes `--remote-debugging-port=0`. It retains Playwright's defaults. Evidence: [repl.py:70–101](../../backend/repl.py#L70).
- In this installed Playwright, Chromium defaults include remote-debugging pipe, headless when requested, no-sandbox unless explicitly enabled, and numerous feature/background switches. **Important correction to generic advice: this installed `chromiumSwitches` list does not include `--enable-automation`.** Do not cite that flag as an observed REPL cause based on older Playwright versions. Evidence: [coreBundle.js:36209–36259](../../.venv/lib/python3.13/site-packages/playwright/driver/package/lib/coreBundle.js#L36209), [44738–44768](../../.venv/lib/python3.13/site-packages/playwright/driver/package/lib/coreBundle.js#L44738).
- Original sandbox launches Chromium directly with fixed debugging port 9222, `/tmp/chrome-profile`, window-size flags, and DISPLAY=:1/Xvfb; its command has neither `--headless` nor `--enable-automation`. Entrypoint prefers Playwright's bundled binary, with system Chromium fallback. Therefore “native launch” here means process ownership/flags, not necessarily stock user Chrome. Evidence: [sandbox/supervisord.conf:10–31](../../sandbox/supervisord.conf#L10), [sandbox/entrypoint.sh:4–27](../../sandbox/entrypoint.sh#L4).
- Sandbox profile restoration occurs before container start by copying the selected profile archive. This differs from the local continuously owned persistent profile. Evidence: [backend/sandbox.py:89–102](../../backend/sandbox.py#L89).
- Local viewer captures via a separate Playwright CDP session (`Page.startScreencast`); fallback screenshots and actions use the owner's Playwright page. Human mouse/key events are HTTP POSTs queued in the viewer, then translated to Playwright mouse/keyboard calls. Chromium's Playwright backend uses `Input.dispatchKeyEvent`/`Input.dispatchMouseEvent`. This is not native OS event forwarding, though it also is not JavaScript `dispatchEvent`. Evidence: [handoff.py:62–135](../../backend/handoff.py#L62), [225–253](../../backend/handoff.py#L225), [coreBundle.js:37162–37246](../../.venv/lib/python3.13/site-packages/playwright/driver/package/lib/coreBundle.js#L37162).
- Original app viewer independently attaches to a target and sends Page screencast/navigation plus CDP Input messages directly. Its viewer attachment does not itself call Runtime.enable, but browser-use remains separately attached. It authenticates ownership, not run-paused state; this handler permits viewer activity while the agent may be running. Evidence: [cdp_proxy.py:40–116](../../backend/cdp_proxy.py#L40), [252–320](../../backend/cdp_proxy.py#L252).
- Local authorization expires with the pending handoff; HTTP middleware serializes actions/resume; held keys/buttons are tracked and released. Viewer JS serializes action promises and drains its release action before resume. These are real coordination improvements, not evidence that challenge acceptance is solved. Evidence: [handoff.py:35–49](../../backend/handoff.py#L35), [106–151](../../backend/handoff.py#L106), [172–201](../../backend/handoff.py#L172), [225–253](../../backend/handoff.py#L225).
- **Confirmed target-consistency defect:** local stream binds once to `pages[-1]` at opening, while every action/screenshot and release selects `pages[-1]` again. A popup/new tab during assistance can make the displayed page differ from the page receiving input. There is no active-target pinning/tab-switch protocol in this viewer. Evidence: [handoff.py:45–49](../../backend/handoff.py#L45), [76](../../backend/handoff.py#L76), [109–110](../../backend/handoff.py#L109), [172–178](../../backend/handoff.py#L172).
- **Confirmed cleanup ordering weakness:** stream cleanup removes its listener, awaits stopScreencast, then detaches; if stopScreencast raises, detach and socket close are skipped. Session creation occurs before the cleanup try/finally. Resume resolves the pending future without awaiting stream cleanup, so agent continuation need not wait for viewer detach. Evidence: [handoff.py:75–104](../../backend/handoff.py#L75), [137–151](../../backend/handoff.py#L137), [182–201](../../backend/handoff.py#L182).
- **Original viewer accumulation candidate:** each tab switch attaches and starts another screencast; `_attach_to_target` overwrites the active session ID without explicitly stopping/detaching the previous session. Inactive frames are ignored before ACK. Connection context exit exists, but switching itself does not clean old sessions. Evidence: [cdp_proxy.py:83–99](../../backend/cdp_proxy.py#L83), [145–150](../../backend/cdp_proxy.py#L145), [194–217](../../backend/cdp_proxy.py#L194), [315–320](../../backend/cdp_proxy.py#L315).

### Inferences
- A working input fixture validates forwarding for its exercised interactions. It does not test ordinary-browser equivalence, detached sessions, or third-party risk decisions. The supplied successful Chromium/WebKit fixture result should remain scoped accordingly.
- Headed mode alone cannot satisfy detach-all-clients: persistent Playwright/browser-use ownership is independent of the headless setting. Likewise changing input transport alone leaves launch/profile/session differences intact.
- The target-selection and cleanup defects are independently actionable architectural problems, but none is established as the cause of the Blinkit access denial.

### Gaps
- Actual executable, argv, profile history, IP reputation and server-side decision for the reported live attempt were not inspected. Sandbox configuration is source-level evidence, not proof of an active deployment's flags or installed versions.
- No claim that the headless setting, webdriver bit, Runtime listeners, cookies, or IP was the decisive Cloudflare input can be made from these files.

## 3. What focused diagnostics could distinguish the hypotheses?

### Takeaway
First test takeover invariants on isolated local fixtures with explicit session accounting. Only separately authorized, bounded website evidence can connect those architectural differences to a Cloudflare decision. Do not replay the blocked challenge as a debugging loop.

### Cited Findings
The proposed tests below target specific code seams: [launch/ownership, repl.py:87–104](../../backend/repl.py#L87); [pause/stream/resume, handoff.py:68–104 and 137–201](../../backend/handoff.py#L68); [Playwright Runtime initialization](../../.venv/lib/python3.13/site-packages/playwright/driver/package/lib/coreBundle.js#L39009); [browser-use actor attachment](../../.venv/lib/python3.13/site-packages/browser_use/actor/page.py#L56); [original viewer attachment](../../backend/cdp_proxy.py#L83).

### Inferences — falsifiable diagnostic plan (not executed)
1. **Pause versus detach:** In a fresh disposable browser on a local page, record protocol sends/receives by connection and session ID before pause, throughout human assistance, and after resume. Include Playwright's owner transport (pipe), browser-use websocket, and viewer session. Assert zero agent tool dispatch during pause separately from zero attached automation sessions. Expected current result: first assertion passes; second fails. Root connection plus target-session accounting is required; websocket counts alone miss Playwright's pipe.
2. **Runtime origin:** On the fixture, compare Playwright owner only, then browser-use attach/observe, then viewer open/close. Count Runtime.enable, target attach/detach and live sessions per step. Hypothesis: closing the viewer leaves owner/actor Runtime-enabled sessions. Falsified if all are proven gone. Do not use a second DevTools client as a supposedly neutral observer without accounting for it.
3. **Actor accumulation:** Repeat `must_get_current_page()` plus observe on a single fixture tab; count attached sessions before/after N operations and after browser-use stop. This distinguishes fresh actor/session accumulation from reuse/automatic cleanup. Do not infer a leak just from Page object allocation.
4. **Target identity:** Open a fixture popup during handoff and show distinct identifiers in each page. Record stream target, input receiver and agent target. Assert all intended to match. Current code predicts screenshot/input mismatch after the popup; this test can establish user-visible impact without a challenge site.
5. **Cleanup/resume boundary:** Exercise normal resume, cancellation, viewer close, page close, stream setup failure and stopScreencast failure on disposable fixtures. Record input release, agent restart, listener removal, screencast stop and detach timestamps. Assert no held input, no surviving viewer sessions and required ordering. Current code predicts detach can be skipped on stop failure and resume can precede detach.
6. **Launch-profile matrix:** With fresh isolated profiles and the same Chromium binary, compare direct headed launch with fixed debug port, Playwright headed persistent, and Playwright headless persistent. Inspect exact argv externally; have the local page itself report UA/webdriver/viewport before adding clients, then after each client attaches. Keep profile and binary fixed to separate launch from instrumentation. This tests fingerprint differences, not acceptance by Cloudflare. Do not add stealth patches or rotate identities as a substitute for diagnosis.
7. **Actual denial evidence:** Ask the site/operator for the already-observed request's Ray ID, timestamp and relevant security event/rule/action when available; distinguish a hard access-denied policy from a solvable interactive challenge. Retain the existing visible error text. Any future live comparison needs separate authorization and fixed account/network/session variables; success once would not establish a general guarantee. Without operator evidence, report correlation only.

### Gaps
- No experiments above were executed. This audit read source/installed package files and current Playwright documentation only; it did not connect to the active browser, send browser input, navigate, replay challenges, or modify application code.
- Bottom line: what is demonstrably wrong is describing a still-instrumented, default-headless remote-input pause as equivalent to a detached native human takeover, plus concrete target/cleanup gaps. The exact reason Cloudflare rejected this browser remains unknown.
