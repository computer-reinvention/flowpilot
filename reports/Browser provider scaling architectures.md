# Browser providers scale by separating lifecycles

**Providers scale asynchronous browser work by separating agent execution, browser ownership, connection lifetime and physical compute residency—not by making Chromium memory disappear when an agent awaits.** Kernel publicly describes the strongest mechanism for retaining live tabs while reclaiming running resources: checkpoint the browser VM’s complete RAM to disk, stop it, then restore it. Browser Use Cloud instead publicly documents isolated Firecracker browser VMs, a custom elastic scheduler and fast startup templates; its current API explicitly loses old tabs and page state after browser expiration, even when a profile survives. Both use more substantial infrastructure than a shared asynchronous Python loop, and Browser Use’s hosted agents run in a separate compute plane from its browsers. The earlier blanket claim that shutting down compute cannot preserve live tabs needs correction: **VM memory snapshots can preserve browser execution state, although remote network sessions and external deadlines are not frozen with it.** For FlowPilot’s full Chromium/Xvfb Docker-per-user deployment with an external agent, the immediate lessons are lifecycle separation, bounded admission and session-affine routing; full-state hibernation is a separately gated engineering project. Neither provider quotas nor the supplied small synthetic local benchmark validate **64 slots on 32 vCPU / 64 GiB**. ([Kernel RAM snapshots](https://www.kernel.sh/blog/scale); [Browser Use browser infrastructure](https://browser-use.com/posts/firecracker-browser-infra); [Browser Use session lifetime](https://docs.browser-use.com/cloud/agent/sessions.md))

Research cutoff: **October 17, 2026**. This report synthesizes the three new research notes in `research_notes/Browser provider scaling architectures/`; the earlier handoff audit supplies only relevant local background. Dated engineering posts are first-party architecture disclosures, their performance figures are **provider-reported measurements**, and live documentation describes the current integration contract. Undated docs and repository `main` references were retrieved by the researchers on the cutoff date and are mutable, not pinned historical evidence. No independent provider benchmark or new local capacity experiment was performed.

## Async preserves ownership; hibernation changes resource residency

“Async across users without losing tabs” contains two different requirements. A scheduler can run user B’s agent while user A awaits an LLM or a human, retaining A’s browser ID and reconnecting to that same browser later. That avoids tying up an orchestration worker, but A’s browser still consumes resources. Reclaiming that browser’s active memory while retaining arbitrary tab state requires a checkpoint mechanism, not just a coroutine, queue, persistent cookie jar or reconnect URL. Browser Use’s definitions are particularly useful: a V4 session is a conversation, a run is one turn, and a browser is the live Chrome instance; a conversation can use multiple browsers, while multiple tabs within one browser do not create additional browser sessions. ([Browser Use concurrency guide](https://docs.browser-use.com/cloud/guides/concurrency.md))

The persistence tiers should be explicit. **Live reconnect** retains the existing process and its tabs while a client detaches. **Profile restore** creates a browser using disk-backed identity/storage and whatever browsing state the profile format supports; it does not promise the former DOM or JavaScript heap. **Full-memory snapshot restore** resumes execution state from a checkpoint, potentially with the hypervisor stopped between uses. Kernel’s full-RAM description and Hypeman’s documented “snapshot to disk, stop hypervisor” operation establish that the third tier is real, rather than merely a theoretical Firecracker feature. The accurate correction to the earlier shutdown claim is therefore: ordinary browser termination plus profile restoration does not preserve arbitrary live state, but stopping a VM **after capturing its memory and required VM state** can. Preserved JavaScript heaps follow from whole-memory checkpointing; their exact behavior across every browser feature was not independently tested here. ([Kernel architecture](https://www.kernel.sh/blog/scale); [Hypeman lifecycle](https://github.com/kernel/hypeman); [Kernel profile semantics](https://www.kernel.sh/docs/browsers/profiles))

The comparison shows a common control-plane pattern rather than a universal isolation model: establish ownership, admit bounded work, route reconnects to the existing placement, and distinguish deletion from disconnection. Browserless makes the routing consequence concrete: an existing session belongs to its original worker, and replacing its reconnect endpoint with an arbitrary load-balancer address can send it to the wrong worker. Cloudflare explicitly permits context multiplexing but recommends a fresh browser when process-level isolation is required; heavy tabs can crash their shared browser. These are alternatives with different failure boundaries, not evidence that Kernel or Browser Use consolidate unrelated users into one Chromium. ([Browserless session affinity](https://docs.browserless.io/enterprise/docker/nginx-load-balancing); [Cloudflare isolation guidance](https://developers.cloudflare.com/browser-run/faq/))

## Kernel turns waiting browsers into snapshots, with important limits

Kernel’s engineering chronology is more informative than a single marketing label. Its **May 26, 2026** account describes moving from warm Docker containers to Unikraft VMs and developing a QEMU path for GPU browsers. It reports paying an initial five-to-ten-second browser initialization cost, capturing the entire in-RAM browser state, and restoring from NVMe in approximately **30 ms**. The **June 5** Firecracker article explains reusable snapshot forks: identity information is injected into guest memory before resume, disks and guest-memory files use **copy-on-write**, and a userfaultfd-based handler brings memory pages in on demand. Forks can benefit from shared snapshot page cache; independently modified tab heaps still require private memory. This amortizes common initialized state rather than eliminating the cost of active browsing. ([May architecture account](https://www.kernel.sh/blog/scale); [June Firecracker implementation](https://www.kernel.sh/blog/firecracker-faster))

The June article also describes an **adaptive internal hot pool**, with burst overflow served through snapshot forks rather than complete boots. It reports 10–30 ms hot handoff, less than 80 ms to connect to Chrome, approximately 1% hot misses, and a closing claim of starts below 20 ms for 99% and below 550 ms for the remaining 1%. These measurements describe different boundaries and the fastest path is already warm; none should be presented as a universal end-to-end cold-start SLA. Customer-configured browser pools are another layer: fixed-size/configuration reservations, explicit acquire/release, and no automatic extra browser when every member is acquired. Their idle capacity is unbilled but counts against concurrency. ([Internal startup design](https://www.kernel.sh/blog/firecracker-faster); [Customer pools](https://www.kernel.sh/docs/browsers/pools))

The **August 4** Hypeman article describes a control plane on a standard PaaS and a data-plane fleet of bare-metal servers. Hypeman is a **single-host runtime**; cross-host scheduling, failover and regional placement sit outside it. It runs ordinary OCI images using a custom initrd, read-only root and writable guest overlay, with resource controls spanning CPU, memory, storage, I/O, bandwidth and vGPU. Firecracker is the efficiency-oriented backend, QEMU supports NVIDIA vGPU needs, and Cloud Hypervisor was being explored for further capabilities. Thus neither “all Kernel browsers are unikernels” nor “all are Firecracker” faithfully summarizes the dated disclosures. Older live unikernel documentation still uses the former framing and has a “sub-millisecond” heading whose body says below 20 milliseconds; the more specific dated accounts take precedence for architecture and timing interpretation. ([Hypeman](https://www.kernel.sh/blog/hypeman); [Older architecture wording](https://www.kernel.sh/docs/info/unikernels))

Kernel does disclose a useful, but non-transferable, density observation: **about 128 running Chromium VMs at 8× CPU oversubscription**, illustrated as a 128-CPU host exposing 1,024 allocated vCPUs to 128 eight-vCPU guests. Its discussion identifies CPU as the hottest resource and projects much higher counts for lighter workloads, explicitly requiring further lifecycle/accounting work for the mid-thousands. This is provider-reported experience, not a matched benchmark. Current product pages describe two vCPUs per session, while limits documentation lists default headful memory of 8 GB and headless memory of 1 GB; these are different configurations from the August illustration, and allocation is not measured RSS. Neither proportional division nor combining those numbers produces a defensible FlowPilot capacity estimate. ([Reported density](https://www.kernel.sh/blog/hypeman); [Browser specs](https://www.kernel.sh/browsers); [Memory allocations and limits](https://www.kernel.sh/docs/browsers/concurrency-and-limits))

### Standby preserves state only within its lifecycle contract

Current standby documentation says a non-GPU browser enters standby after **five seconds** with no CDP client, WebDriver/BiDi client, Live View viewer or in-flight computer-controls request. Usage charges stop, and its deletion timeout begins; the default timeout is **60 seconds**, configurable up to **72 hours**. **GPU browsers do not support standby. Standby does not release the concurrency slot.** Current organization tiers of 5, 10, 150 or custom browsers are account entitlements, not host packing limits. A permanently attached agent or open viewer therefore materially changes the integration: merely awaiting without sending commands is not documented to trigger standby. ([Standby](https://www.kernel.sh/docs/browsers/standby); [Termination](https://www.kernel.sh/docs/browsers/termination); [Concurrency](https://www.kernel.sh/docs/browsers/concurrency-and-limits))

There is a genuine source conflict: the May engineering article says an ingress proxy can hold the CDP connection while the VM sleeps, whereas current lifecycle docs classify a connected CDP client as active. **Design against the current documented disconnect requirement**, not the historical transparent-sleep description. Kernel separately documents that Playwright/Puppeteer `browser.close()` does not delete its managed browser; the Kernel deletion operation ends the session. Its FAQ says CDP WebSockets can close after about an hour while the browser persists, permitting reconnection to the same endpoint within the browser’s lifecycle. These are Kernel-specific managed-session semantics, not instructions to apply indiscriminately to local Chromium or Browserless. ([Historical proxy behavior](https://www.kernel.sh/blog/scale); [Current standby policy](https://www.kernel.sh/docs/browsers/standby); [Termination](https://www.kernel.sh/docs/browsers/termination); [FAQ](https://www.kernel.sh/docs/browsers/faq))

**RAM continuity does not guarantee network continuity.** Kernel’s **September 1** proxy engineering post reports that a per-VM Envoy slept with the browser and woke with stale upstream connections/configuration; observed first-connection failure rates after idle were 20–26.7%. Its replacement moved proxy management to an always-on host-side Go service with fresh request paths. The claimed 92% improvement measures time to the **first successful network request after standby**, not raw VM restore latency. This is direct evidence that a browser can retain its memory yet need network repair after wake. Remote TCP/WebSocket/WebRTC peers, authentication lifetimes and server-side deadlines continue advancing while the guest is stopped; guest JavaScript and downloads do not keep executing during stopped-hypervisor standby. ([Proxy redesign and benchmark definition](https://www.kernel.sh/blog/proxy); [Stopped-hypervisor lifecycle](https://github.com/kernel/hypeman))

Profiles and pools introduce another boundary. Kernel profiles snapshot Chromium’s user-data directory, including documented open-tab/browsing state, but that wording is not a promise to preserve identical DOM, heap or pending requests. Changes save on deletion/timeout with `save_changes`, not on CDP disconnection; a save replaces the whole stored profile, so one writer per profile is the safe contract. Pool `reuse: true` literally hands the same unchanged browser—including tabs and identity—to its next acquirer. Kernel’s per-user recommendation attaches the user’s profile and releases with `reuse: false`, preserving profile data while destroying that VM’s live state. A generic reusable pool is therefore not automatically a safe per-user session swapper. ([Profiles](https://www.kernel.sh/docs/browsers/profiles); [Pool reuse](https://www.kernel.sh/docs/browsers/pools))

Public unknowns remain material: the fleet placement algorithm, host autoscaler, snapshot replication/transport, dirty-memory write costs and current crash-recovery guarantees are not established by these sources. The May account explicitly acknowledged host-pinned snapshots vulnerable to host/disk/power failure; subsequent migration discussion is not a blanket durability guarantee. Kernel establishes the **mechanism** for memory-preserving standby, not an independently verified promise that every live browser survives every failure. ([Historical durability limits](https://www.kernel.sh/blog/scale); [Fleet/runtime boundary](https://www.kernel.sh/blog/hypeman))

## Browser Use scales browser VMs separately from agent runners

The MIT `browser-use` Python library and the proprietary Cloud service are distinct. The library can run an agent locally or against a remote browser; the Cloud browser service hosts the browser, while the fully hosted API also executes the agent. Reading an open-source `BrowserSession` class does not reveal the hosted scheduler. For FlowPilot, whose agent already runs outside the browser container, **standalone browser infrastructure over CDP is the relevant integration boundary**; adopting the hosted agent runtime is optional. ([Project README](https://github.com/browser-use/browser-use); [Standalone browser quickstart](https://docs.browser-use.com/cloud/browser/quickstart.md))

The **June 15, 2026** infrastructure post states that each Cloud browser session gets its own small Firecracker VM running headless Chromium, with its own filesystem, cookies/cache, proxy and downloads. Firecracker runs nested on regular EC2 instances rather than requiring bare-metal hosts. A custom control plane chooses a host with room, scales hosts out, and drains hosts by stopping new placement. It tracks starting browsers, draining hosts and excluded hosts in real time rather than relying on minute-scale CloudWatch windows. Prebuilt host images make new hosts ready to serve browsers about **30 seconds** after launch. Stateless edge routers consult placement and forward CDP WebSocket bytes; placement is a control-plane responsibility, not a side effect of choosing a WebSocket router. ([Browser architecture](https://browser-use.com/posts/firecracker-browser-infra))

Its CPU scheduling details are unusually concrete. Browser vCPUs start **unpinned** to avoid constraining Chromium’s startup burst, then are pinned after CDP readiness. Placement allocates both sibling hyperthreads of a physical core, and pinned vCPU threads receive real-time priority. The provider reports changing early losses from 17% to zero in a 1,000-browser test after that priority change. This supports the importance of CPU placement and contention management; **1,000 browsers in a test is not 1,000 browsers on one host**. Host instance types, per-browser RAM/vCPU budgets, oversubscription ratios, packing algorithm and production spare capacity remain undisclosed in the inspected sources. ([CPU placement and test](https://browser-use.com/posts/firecracker-browser-infra))

Startup optimization is also specific: a production template resumes a VM **already booted and paused just before Chromium launches**. The implementation uses 2 MB pages, a custom userfaultfd handler to prefetch hot pages, removal of unnecessary PS/2 probing, and readiness signals through vsock/logs instead of HTTP polling. The provider reports final VM cold start below 400 ms and public create latency of **825 ms p50 / 1.35 s p99** over 10,000 successful sessions. Host-image preparation and VM startup templates are public prewarming mechanisms; a particular ongoing hot-browser pool size/policy is not disclosed. The same June post identifies snapshotting **after** Chromium starts as future work. A clean startup snapshot must not be relabeled as a checkpoint of a user’s populated tabs, and the reviewed sources did not establish that roadmap as shipped by the cutoff. ([Startup mechanism and roadmap](https://browser-use.com/posts/firecracker-browser-infra))

The agent plane changed on a separate timeline. A **February 25** account described Unikraft agent microVMs on dedicated AWS bare metal with idle suspend/resume. The **July 12** migration post instead describes one AgentCore microVM per hosted agent session, using `runtimeSessionId = session_id`, while the control plane runs on ECS Fargate behind an ALB and scales independently. A session-scoped **1 GB durable workspace** stores files and `bcode.db`; the post specifies agent idle stop at 15 minutes and an eight-hour maximum lifetime, with mount retention bounded by version changes or 14 days idle. These are agent-runtime/file-recovery rules, **not browser-tab retention rules**. The post’s broad statement about outbound mediation is narrowed by its own public-HTTPS CDP and presigned-transfer paths; the supported security reading is credential mediation, not that every byte necessarily traverses the control plane. ([Historical agent design](https://browser-use.com/posts/two-ways-to-sandbox-agents); [AgentCore migration](https://browser-use.com/posts/agentcore-migration))

### Current API semantics retain live browsers temporarily, not indefinitely

Hosted work is asynchronous: create a run, keep its run/session identifiers, then poll status/events. A client-side wait timeout does not cancel the server-side run. V4 permits one active run per conversation; overlapping direct follow-ups return 409, and the per-session queue holds 20 pending messages before returning 429. That queue is not a project-wide batch scheduler or capacity reservation. The official guidance is to keep large batches in the application’s own queue, admit a bounded number, and track job, conversation, run and browser identifiers separately. This is precisely the coordination layer FlowPilot should own even when it buys browser execution. ([Sessions](https://docs.browser-use.com/cloud/agent/sessions.md); [Concurrency and batch guidance](https://docs.browser-use.com/cloud/guides/concurrency.md))

An agent browser normally remains idle for about **120 seconds**, effectively two to three minutes because cleanup runs every minute. V4 `keepAlive` is an integer from 120 to 14,400 seconds, distinct from older V2/V3 boolean semantics, and cannot exceed the browser’s four-hour hard lifetime. The current docs are explicit: **“A later follow-up gets a fresh browser with the same settings and profile, but not the old tabs or page state.”** Reusing a still-open browser emits `browser.reattached`. Human handoff therefore requires finishing at a checkpoint, reserving enough keepalive time, letting the user act, and continuing within that browser’s lifetime—not simply retaining a conversation ID. ([Current session semantics](https://docs.browser-use.com/cloud/agent/sessions.md); [Human handoff](https://docs.browser-use.com/cloud/agent/human-in-the-loop.md))

Standalone browsers, the closer fit for FlowPilot, return a browser ID, `cdpUrl`, `liveUrl` and `timeoutAt`. Their timeout is in **minutes**, default 60 and range 1–240; documented status is `active` or `stopped`. Closing the CDP client, Playwright browser connection or SDK client does not stop the managed browser; stopping requires the Cloud API. Profiles retain cookies, local storage and login state, with one profile recommended per end user. They do not restore the old loaded pages; exact concurrent-writer and failure-time save semantics are public unknowns. ([Create schema](https://docs.browser-use.com/cloud/api-v4/browsers/create-browser-session.md); [Quickstart](https://docs.browser-use.com/cloud/browser/quickstart.md); [Profiles](https://docs.browser-use.com/cloud/guides/authentication.md))

Billing and quota illustrate why logical concurrency cannot be read as density. Current published browser pricing is **$0.02/browser-hour**, excluding agent and proxy costs. A standalone browser holds a concurrency slot until stopped; a hosted V4 conversation consumes a slot only while a run is queued/running, although its idle browser remains billable. Project payment tiers currently advertise 10 through 1,000 concurrent sessions, subject to existing grants/account restrictions. These are service entitlement rules; neither an idle browser’s slot exemption nor AgentCore’s idle economics establishes zero browser resource consumption. Browser Use’s historical Unikraft standby claims also do not override the current explicit tab-loss-on-expiry contract. ([Pricing](https://browser-use.com/pricing); [Accounting rules](https://docs.browser-use.com/cloud/guides/concurrency.md); [Historical/current browser transition](https://browser-use.com/posts/firecracker-browser-infra))

## FlowPilot should stage lifecycle changes before promising density

The current local baseline is **full Chromium/Xvfb Docker per user for both the REPL and app, with the agent outside**. As supplied by the parent session after the earlier audit, `backend/repl.py` now defaults to `browser_mode='sandbox'`; native headless execution remains optional through `--browser-mode native`. The earlier audit’s description of a normally headless REPL is historical and does not describe this updated default. The baseline already separates agent and browser compute conceptually, but does not thereby acquire provider-grade admission, placement or snapshotting. Browser Use’s fully headless design suggests a worthwhile compatibility/performance experiment against the sandbox’s display stack, not a guaranteed drop-in density improvement. Moving from containers to microVMs similarly changes isolation and checkpoint opportunities; it does not remove Chromium’s working set. ([Historical local sandbox audit](../research_notes/Browser%20handoff%20architecture%20review/local_audit.md); [Browser Use headless design](https://browser-use.com/posts/firecracker-browser-infra))

**The first stage should establish lifecycle and ownership correctness while retaining the current browser boundary.** Maintain separate user/profile, browser-session, task/run, placement and tab-target identities. Define running, waiting-with-live-browser, human-control, expired and failed states; add suspended/restoring only when implemented and verified. Use a bounded application queue plus per-host CPU/memory admission, route reconnects to the owning worker, and drain occupied workers before removal. Serialize conflicting human/agent actions and pin stream/input to the same target across popups and tab changes. The earlier handoff audit already found target-selection and cleanup-ordering defects, making this an immediate correctness requirement rather than speculative scaling machinery. Browserless’s limiter and Cloudflare’s coordinator guidance provide public patterns; they do not supply FlowPilot’s measured limits. ([Local handoff evidence](../research_notes/Browser%20handoff%20architecture%20review/local_audit.md); [Browserless limiter](https://github.com/browserless/browserless/blob/main/src/limiter.ts); [Cloudflare coordination](https://developers.cloudflare.com/browser-run/features/reuse-sessions/))

**The second stage should measure active capacity and introduce only justified warm capacity.** The supplied approximately 0.7 GiB/0.35-core synthetic per-session result and 64-slot forecast are contextual inputs, not independently audited findings of this research. A small constrained benchmark does not capture synchronized navigation, growing tab heaps, human viewing, recording, shared-memory pressure or long-lived leaks. Measure the proposed 32-vCPU/64-GiB host with representative sites and tab counts, active versus LLM-wait versus human-wait duty cycles, realistic launch bursts, long-duration host memory/RSS/PSS, CPU throttling, p95/p99 action latency and crash/OOM rates. Record total host consumption, not only summed process RSS, especially where pages are shared. Choose admission below the observed latency/failure knee with explicit operating-system, proxy, streaming and startup reserves; “64” remains a hypothesis until that workload passes.

Public comparison numbers cannot fill that evidence gap. Browserless recommends 2 cores/4 GB for 5–10 sessions, 4 cores/8 GB for 10–20, and 8+ cores/16+ GB for 20–50, but supplies no matched workload or reproducible density experiment. Browserbase’s Firecracker explainer quotes less than 5 MiB of **VMM bookkeeping before guest workloads**, not a five-megabyte browser. Its warm-pool engineering article also notes video encoding competing for host CPU. Kernel’s 128-VM observation uses different hardware/configuration; Browser Use does not disclose per-host counts. **Cloud quota, configured concurrency, total fleet test size, VMM overhead and measured host browser density are five different quantities.** ([Browserless sizing guidance](https://docs.browserless.io/enterprise/docker/enterprise-image); [Firecracker overhead definition](https://www.browserbase.com/blog/what-is-firecracker); [Warm pools and recording](https://www.browserbase.com/blog/build-vs-buy-agent-infrastructure); [Kernel host example](https://www.kernel.sh/blog/hypeman))

**The third stage should prototype memory-preserving standby separately from profile recovery.** Kernel is the clearest documented managed candidate for this requirement, subject to disconnect rules, retained concurrency slots, GPU exclusions and verified recovery behavior. A self-hosted Hypeman/microVM experiment would need snapshot storage, lifecycle admission, stable session routing and a wake path; these are additional engineering obligations beyond wrapping the existing Docker image. Acceptance should exercise multiple tabs, a DOM-only mutation, unsaved forms, JavaScript-held state, delayed timers, downloads, WebSockets and reconnect after an idle interval. Verify both retained state and honest recovery from expired external connections; measure checkpoint cost, snapshot footprint, restore-to-interactive latency and host-failure behavior separately. Do not promise every arbitrary browser application resumes transparently simply because a memory image restores. ([Kernel runtime](https://github.com/kernel/hypeman); [Standby integration constraints](https://www.kernel.sh/docs/browsers/standby); [Network recovery evidence](https://www.kernel.sh/blog/proxy))

A profile-only fallback should be a deliberate user-visible downgrade: identity/storage restored, pages reconstructed, unsaved live state potentially lost. Long-lived personal desktops and bounded task browsers are different products. Browser Use’s documented four-hour standalone limit fits bounded external-agent jobs and human handoffs; it does not establish indefinite desktop continuity. Kernel’s up-to-72-hour standby timeout and slot retention impose different operational and commercial bounds. Establish those lifecycle promises before deciding whether to buy a provider, scale Docker workers or build a snapshot substrate. These are staged recommendations only; this research makes no production implementation changes. ([Browser Use lifetime](https://docs.browser-use.com/cloud/api-v4/browsers/create-browser-session.md); [Kernel retention](https://www.kernel.sh/docs/browsers/termination); [Kernel slot accounting](https://www.kernel.sh/docs/browsers/concurrency-and-limits))

## Conclusion

The decisive architecture choice is **what FlowPilot promises to preserve, for how long, and through which failures**. Exact live state during a brief handoff calls for a leased browser with reliable ownership; exact state across compute reclamation calls for memory checkpointing plus network-aware recovery; durable login alone calls for a profile. Giving these distinct guarantees explicit names prevents a cheap profile restart from being sold as lossless resume and prevents an async scheduler from being mistaken for a browser-density optimization.

Kernel provides public evidence that full-state browser standby is achievable. Browser Use provides unusually concrete evidence for browser/agent separation, elastic host management and CPU-aware scheduling, while its current lifetime contract establishes a different persistence boundary. FlowPilot can adopt their control-plane lessons first and benchmark its own workload before committing to a capacity number. The outcome to optimize is reliable retained user state at an acceptable active-resource and recovery cost—not the largest advertised concurrency figure.
